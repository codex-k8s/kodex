# Автоматизации и управляемые процессы

## Управляемый процесс

`Playbook` является версионируемым процессом, управляемым промптом и policy revision, а не визуальным графом действий.

Он содержит:

- входную JSON Schema;
- политику агента-координатора;
- шаблон инструкции Markdown;
- разрешенных агентов и интеграции;
- параллельность и тайм-аут;
- контракт обратного вызова;
- критерии завершения;
- шлюзы ручной приемки;
- схему результата.

`ProcessRun` фиксирует версию playbook, policy revision и корневого человеческого инициатора. Изменение `Playbook`, имен ролей или связей не меняет уже запущенный процесс.

Платформа не распознает полномочия по именам `director`, `manager` и аналогичным. Пресет верхнеуровневого координатора обычно запускает координаторов волн и получает их callbacks, а пресет координатора волны запускает рабочие роли. Проект может переименовать роли и изменить разрешенный граф.

Управляемый процесс проверки передаёт каждой разрешённой роли независимой или security-проверки общий контракт исходов `Merge blocker|MVP follow-up|Informational`. Результат проверки для каждого GitHub review thread содержит его URL или node ID, выбранный исход и доказательство закрытия. `MVP follow-up` дополнительно содержит URL Issue с label `mvp-follow-up`, предметный label и причину, по которой замечание не является blocker; эти поля появляются до разрешения thread.

Шлюз слияния читает GitHub GraphQL `reviewThreads` и отклоняет unresolved thread либо thread без допустимого исхода. Плоский список комментариев и отсутствие `check runs` не удовлетворяют шлюзу. После изменения head SHA прежнее одобрение не переносится: запускается полный повторный проход точного SHA.

## Координация между обсуждениями

Координатор использует MCP согласно своим capabilities:

- `mattermost_start_agent_thread`;
- `mattermost_return_to_requester`;
- `request_human_gate`;
- `report_process_status`;
- `publish_artifact`.
- `mattermost_request_owner_attention`;
- `mattermost_list_active_work`;
- `mattermost_request_sync`.

Дочернее обсуждение хранит идентификатор родительского процесса. Событие завершения ставит обратный вызов в очередь сессии менеджера. Обратный вызов не зависит от упоминания Mattermost и не запускается повторно при повторной доставке события.

Перед межкомнатным запуском координатор проверяет каталог и карточку целевого чата. Доменный сервис проверяет relationship rule, сохраняет точное сообщение запуска и наследует root initiator. Дочерняя роль возвращает результат непосредственному разрешенному координатору через долговечный callback. Обычный callback и завершение не упоминают человека. Ручной шлюз создается через `mattermost_request_owner_attention`, а окончательная runtime-ошибка маршрутизируется платформой корневому инициатору.

## AutomationSchedule

Цель расписания:

- конкретный `Agent`;
- версия `Playbook`.

Поля:

- cron или интервал;
- часовой пояс IANA;
- промпт и его версия;
- политика сессии `new|persistent|rolling`;
- параллельность `forbid_overlap|queue_all|coalesce`;
- обработка пропущенного запуска `skip|run_once|catch_up|within_grace_period`;
- уведомления `always|on_action|on_failure|on_action_or_failure|audit_only`;
- целевая комната;
- максимальное время выполнения и политика повторов.

Рекомендуемые значения по умолчанию: `new`, `coalesce`, `run_once`, `on_action_or_failure`.

## Долговечное планирование

Пользовательские расписания хранятся в PostgreSQL. Планировщик выбирает наступившие записи через `FOR UPDATE SKIP LOCKED`, создает экземпляр расписания и задание очереди в одной транзакции. Уникальный `(schedule_id, scheduled_for)` предотвращает дубли.

River рассматривается как очередь выполнения в PostgreSQL для транзакционной постановки заданий и повторов. Его планировщик в памяти не является источником истины; следующий запуск и правила пропущенных запусков реализуются доменной моделью. Cron разбирается готовой библиотекой, а не собственным синтаксическим анализатором.

Kubernetes CronJob не используется для пользовательских расписаний: он не знает о сессиях, привязке поставщика, правах, согласованиях и доставке Mattermost.

## Выполнение без чата

`ScheduledRun` может не иметь `ConversationBinding`. При `no_action` результат остается в аудите. При выполненном действии или ошибке система создает сообщение Mattermost согласно политике доставки. Агент может через MCP создать отдельные обсуждения и делегированные запуски.

## Процесс ручной приемки результата

`Playbook` для разработки или документации должен поддерживать:

1. результат исполнителя;
2. 2-3 цикла рецензирования;
3. проверку готовности менеджером;
4. замечания владельца;
5. исправления исполнителя;
6. финальный цикл рецензирования;
7. финальный OK владельца;
8. обратный вызов рецензента менеджеру с проверкой актуального SHA и замечаний;
9. слияние менеджером;
10. для обычного принятого результата — запуск `improver` менеджером по замечаниям цикла;
11. подготовку `improver` отдельного результата в собственных Issue и PR;
12. трактовку обратного вызова `improver` только как готовности отдельного результата к рецензированию;
13. независимое полное рецензирование, ручные шлюзы владельца и проверку после финального OK для результата `improver`;
14. слияние принятого результата `improver` только менеджером с защитой точного SHA;
15. разрешение зависимой реализации только после этого слияния;
16. терминальное завершение исходного цикла без автоматического рекурсивного запуска нового `improver`.

После каждого обычного слияния отдельный шаг портфельной координации выбирает открытые Issues с label `mvp-follow-up` и формирует из них ограниченную неблокирующую волну. Состав волны и разрешённые связи остаются данными версии `Playbook` и policy revision; имена ролей не кодируют полномочия. Волна не блокирует независимую MVP-разработку и не применяется к слиянию результата текущего цикла `improver` как основание для рекурсивного запуска.

Обычным является результат, который не создан в рамках текущего цикла `improver`. Новый `improver` после слияния результата улучшения процесса возможен только как отдельно обоснованная работа по новому материальному замечанию, а не из-за самого факта слияния.

Следующая независимая волна может стартовать параллельно, если не зависит от непринятого результата.
