# Карта интеграций

## Типы интеграций

### Прямая интеграция среды выполнения

Утилита и учетные данные предоставляются pod агента напрямую. Режим подходит для доверенных сценариев, где согласование человеком не должно быть технически обязательным.

Примеры:

- `gh` с ограниченным токеном GitHub;
- `kubectl` только для чтения с выделенным kubeconfig;
- локальные инструменты языка и сборки без учетных данных.

Прямой режим нельзя использовать, если платформа обязана гарантировать согласование перед изменением: агент уже имеет учетные данные и способен обойти шлюз.

### Управляемая интеграция MCP

Агент получает только MCP endpoint с областью одной сессии. Шлюз интеграций владеет учетными данными и выполняет инструмент после проверки прав, риска и согласования.

Примеры:

- запись/проведение документа в 1С;
- отправка договора или письма клиенту;
- изменение сделки CRM;
- финансовая операция;
- изменение промышленного кластера Kubernetes;
- изменение настроек MatterCodex.

Текущий доказанный вертикальный срез находится внутри bot-service и предоставляет только `deployment.restart_workload@1`. Несмотря на имя capability, единственный адаптер `recording_test` записывает квитанцию в PostgreSQL и не изменяет Kubernetes или внешнюю систему. Connection не содержит рабочего endpoint или credential, а runtime-путь не импортирует Kubernetes SDK и не вызывает `kubectl`.

## Целевая материализация MCP в Codex

В будущем перед каждым `exec/resume` объект `RuntimeRevision` будет собирать разрешенные агенту привязки MCP. Материализация отдельных секций `[mcp_servers.<stable_name>]` в сгенерированный `config.toml` Codex не входит в Issue #93.

Реализованный срез использует уже существующий session-scoped HTTP MCP endpoint bot-service. При создании MCP-сессии сервер формирует каталог по свежему server-side grant, а каждый вызов повторно аутентифицирует bearer сессии. Запрещённая capability отсутствует из `tools/list`; угаданный вызов не достигает доменного сервиса.

Для секции задаются транспорт, endpoint или команда, `required`, разрешенные инструменты, безопасные ссылки на заголовки из переменных окружения, `startup_timeout_sec` и `tool_timeout_sec`. Значения секретов в TOML не записываются. `tool_timeout_sec` устанавливается в максимальное разрешенное установленной версией Codex и политикой платформы значение, чтобы обычные долгие операции не обрывались преждевременно.

Тайм-аут не является механизмом многодневного ожидания решения человека. Такие действия используют долговечное продолжение сессии, описанное ниже.

### Интеграция чтения и контекста

Интеграция предоставляет ограниченный поиск и чтение данных. Выдача ограничивается областью, пагинацией и бюджетом контекста.

## Пакет интеграции

Версионируемый пакет YAML содержит:

```yaml
apiVersion: mattercodex.io/v1alpha1
kind: IntegrationDefinition
metadata:
  name: example-crm
spec:
  connectionSchema: {}
  capabilities: []
  runtime:
    mode: managed-mcp
  tools: []
  riskPolicies: []
  promptDocumentation: "..."
  healthCheck: {}
```

Пакет не содержит значений секретов. Поля проходят проверку JSON Schema. Произвольные действия MCP используют декларативный подход, совместимый по идее с `yaml-mcp-server`, но промышленный шлюз дополнительно обеспечивает разделение организаций, авторизацию, права, аудит и согласования Mattermost.

## Карта внешних систем

| Система | Роль | Базовый режим |
| --- | --- | --- |
| Mattermost | Обсуждения, учетные записи, файлы и согласования | Нативный адаптер |
| OpenAI Codex | Первый поставщик среды выполнения агента | Адаптер поставщика и device-code авторизация |
| GitHub | Репозитории, Issues, PR и рецензирование | Прямой `gh` или управляемый MCP по политике |
| Kubernetes | Среда платформы и целевых проектов | Прямой режим только для чтения; изменения через управляемый MCP либо явный профиль администратора |
| S3 | Файлы, архивы сессий и резервные копии | Адаптер платформы |
| Электронная почта | Прием и исходящая коммуникация | Управляемый MCP |
| CRM/1С | Бизнес-операции | Управляемый MCP с согласованиями |
| OCI registry | Образы платформы и ролей | Адаптер цепочки поставки |

## Контракт согласования

Каждая возможность имеет класс риска:

- `read` - согласование обычно не нужно;
- `write` - определяется политикой;
- `external_communication` - согласование по шаблону или получателю;
- `destructive` - обязательное согласование;
- `financial` - обязательное согласование и дополнительные метаданные аудита;
- `platform_admin` - обязательное согласование либо явно разрешенный аварийный профиль.

Согласование показывает инициатора, цель, инструмент, безопасные аргументы, риск, срок действия и ожидаемый эффект. Секретные аргументы маскируются до сохранения запроса.

## Целевое долговечное ожидание согласования

1. Уже реализовано: MCP-вызов создаёт `ToolInvocation` и `ApprovalRequest` в одной транзакции и немедленно возвращает структурированный `pending`.
2. Уже реализовано: exact human decision атомарен с погашением callback capability, а recording execution и immutable receipt сохраняются идемпотентно независимо от agent pod.
3. Уже реализовано: повтор исходного MCP-вызова с тем же ключом и binding читает сохранённый результат.
4. Не реализовано: перевод AgentSession в `waiting_approval`, сохранение специального архива для согласования и удержание PVC.
5. Не реализовано: outbox события автоматического продолжения, новый ход, восстановление архива и Codex `resume`.
6. Не реализовано: автоматическое продолжение после отклонения, истечения срока или ошибки.

Открытый MCP-запрос уже не удерживается в ожидании человека. Корреляция выполняется по неизменяемому идентификатору вызова, двум binding hash и execution fence; автоматическое продолжение с пятницы до понедельника потребует отдельной реализации.

Fresh authorization выполняется непосредственно перед первой записью recording receipt. Отзыв до этой границы оставляет ноль квитанций и переводит invocation в `cancelled`; квитанция, уже зафиксированная до сбоя или позднего отзыва, является неизменяемым фактом и при восстановлении финализируется с тем же fence/hash без второго side effect.
