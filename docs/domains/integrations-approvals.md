# Интеграции и согласования

## Назначение

Управляет декларативным каталогом интеграций, соединениями, возможностями, правами, выполнением MCP и ручными согласованиями.

## Основные сущности

- `IntegrationDefinition` — schema-versioned YAML package с origin и
  canonical digest, типизированными capabilities и закрытым adapter key.
- `IntegrationConnection` — public configuration и pin определения конкретной
  организации.
- `IntegrationCredentialRevision` — только ref Kubernetes Secret, UID,
  `resourceVersion` и digest содержимого; secret value не является domain data.
- `IntegrationCapability` — именованная операция со схемой входа и выхода и уровнем риска.
- `IntegrationGrant` — право Agent или Workflow на возможность с ограничениями.
- `IntegrationInvocation` — fenced идемпотентный вызов из конкретной Session,
  Turn и attempt.
- `IntegrationEffectReceipt` — неизменяемое доказательство одного provider
  effect с effect/input/response digests и provider ref.
- `HumanGate` — единое долговечное one-winner решение человека, которым владеет
  control-plane.
- `IntegrationApprovalScope` — выданное владельцем после Human Gate право на
  повторные вызовы одной возможности при совпадении выбранных типизированных
  параметров. Оно не является правом на другие возможности или запуски.

## Выполнение

1. Токен с областью одной Session и attempt аутентифицирует runtime caller.
2. Шлюз проверяет определение, версию и работоспособность соединения.
3. Вычислитель политик проверяет право и ограничения.
4. READ переходит в `READY`. WRITE, SENSITIVE и DESTRUCTIVE используют
   утверждённый режим согласования: `HUMAN_EACH_EFFECT` создаёт отдельный
   Human Gate; `HUMAN_SCOPED` сначала ищет действующее право на точный scope,
   иначе в той же транзакции создаёт Human Gate и переходит в
   `WAITING_APPROVAL`.
5. Worker claim для защищённого effect разрешён только после `APPROVED`.
6. Согласованное действие выполняется закрытым типизированным adapter-ом.
7. Успех атомарно фиксирует terminal invocation и одну immutable effect
   receipt; exact retry читает её, а несовпадение закрыто отклоняется.

## Настройка credential

Connection и credential создаются двумя командами. Browser сначала создаёт
Connection без secret metadata. Затем специализированная команда с OCC и
semantic idempotency передаёт значение доверенному materializer. Он записывает
детерминированный data key в единственный Kubernetes Secret и возвращает
server-owned metadata; только после этого control-plane создаёт immutable
revision и активирует её. Повтор того же idempotency key с другим значением
запрещён. Публичный readback содержит только маскированное состояние.

## Контракт MCP среды выполнения

- Каждая разрешённая привязка MCP входит в `RuntimeRevision` и материализуется
  provider adapter-ом перед запуском или возобновлением provider session.
  Codex adapter использует отдельную секцию `config.toml` и app-server
  `thread/start|resume`; это не часть core domain model.
- Выданное право ограничивает список инструментов; агент не видит запрещенные возможности даже в каталоге инструментов.
- Секрет используется через токен сессии или ссылку на заголовок из переменной окружения и не записывается в TOML, промпт или аудит.
- Startup/tool timeout вычисляются из проверенной политики и возможностей
  выбранного provider adapter; Codex adapter ограничивает их возможностями
  установленной версии Codex.
- Изменение соединения, права, endpoint или тайм-аута изменяет `RuntimeRevision` и применяется к следующему ходу.

## Продолжение после отложенного согласования

Многодневное решение человека не удерживает запрос MCP открытым. Шлюз возвращает
`pending`, Session сохраняется, а Run переходит в `WAITING_HUMAN`. После
согласования, отклонения или истечения срока выполнение и результат фиксируются
идемпотентно, а долговечное событие создаёт Turn продолжения исходной Session.

Продолжение содержит идентификатор вызова, безопасное обозначение инструмента,
хеш аргументов, решение и структурированный результат или ошибку. Среда
выполнения восстанавливает ту же provider session под той же учётной записью
ИИ. Codex adapter обновляет `config.toml` и выполняет app-server
`thread/resume`. Ожидающее
согласование блокирует очистку PVC и архива сессии, но не удерживает pod.

## Жизненный цикл согласования

Состояния invocation: `WAITING_APPROVAL`, `READY`, `RUNNING`, `SUCCEEDED`,
`FAILED`, `REJECTED`, `CANCELLED`. Решение Human Gate принимается до claim и
может быть только `APPROVE`, `REJECT` или `CANCEL` для integration effect.

Для `HUMAN_EACH_EFFECT` решение связывается с хешем полного вызова инструмента;
изменение аргументов создаёт новый запрос. Режим `HUMAN_SCOPED` является
отдельным вариантом, а не неявным ослаблением существующих возможностей:

- Владелец задаёт в `IntegrationGrant` непустой упорядоченный набор путей JSON
  Pointer к полям опубликованной входной схемы возможности. Пути и типы полей
  проверяются при настройке права. Модель не выбирает scope и не передаёт его
  через параметры вызова.
- Карточка согласования показывает конкретные значения выбранных полей и явно
  перечисляет остальные поля как изменяемые между вызовами. Одобрение создаёт
  immutable scope: организация, проект, соединение, digest определения и
  схемы, возможность, версия права, авторитетно разрешённые агент и root Run,
  канонические пути, типизированные значения и их digest, срок действия и
  верхняя граница числа эффектов. Пустой набор путей, wildcard и неполное
  значение запрещены. `agentRef` и `runRef` не берутся из payload модели.
- Для каждого нового вызова control-plane сначала проверяет действующий grant,
  состояние root Run, актуальность определения/права и совпадение канонических
  типизированных значений по всем путям. Несовпадение или истечение срока
  создаёт новый Human Gate. Повторный вызов использует новое собственное
  `IntegrationInvocation`, effect key, fence и receipt; одно согласование не
  является идемпотентным ключом для нескольких внешних эффектов.
- Отклонение не создаёт scope. Отмена, terminal или retry запуска, отзыв права,
  отключение соединения, смена определения/схемы/набора путей и истечение срока
  отзывают scope атомарно с переходом владельца. Уже заявленный эффект
  завершается по существующему fenced/unknown-outcome протоколу; новый claim
  после отзыва запрещён.

## Опасные действия

Учетные данные для опасной возможности не материализуются в pod. Нельзя одновременно требовать обязательное согласование и выдавать агенту прямые учетные данные, позволяющие выполнить то же изменение в обход шлюза.

## Критерии приемки

- Проверка соединения не раскрывает секрет.
- Агент видит только разрешенные инструменты.
- Карточка согласования не требует ввода команды или идентификатора.
- Повторное согласование или повтор не выполняют изменение дважды.
- Результат отклонения или истечения срока понятен агенту.
- Инструмент, решение и выполнение имеют единую цепочку корреляции.
- Согласование может ожидать несколько суток без живого pod и после решения продолжает исходную сессию.
- Обновление среды выполнения не теряет разрешенные серверы MCP и не раскрывает их учетные данные.
