# Автоматизации и процессы

## Назначение

Владеет `Playbook`, `ProcessRun`, графом дочерних запусков, обратными вызовами, ручной приемкой, `AutomationSchedule` и `ScheduledRun`.

## Правила расписания

- Часовой пояс обязателен и хранится как имя IANA.
- Интерфейс предлагает готовые варианты; cron доступен в расширенных настройках.
- `coalesce` является политикой параллельности по умолчанию.
- `run_once` является политикой пропущенного запуска по умолчанию.
- `on_action_or_failure` является политикой уведомлений по умолчанию.
- «Запустить сейчас» создает отдельный экземпляр и не сдвигает следующий плановый запуск.

## Результат запуска по расписанию

Результат: `no_action`, `action_taken`, `requires_human`, `failed`.

`no_action` может не создавать сообщение Mattermost. `requires_human` всегда создаёт доступную ручную приёмку и оставляет запуск в `waiting_owner` до решения корневого инициатора. История и аудит сохраняются для всех результатов.

Принятие `requires_human`, сохранение точного callback hash, создание одного `OwnerAttentionRequest` и переход `ScheduledRun`/occurrence/`ProcessRun` в ожидание являются одной PostgreSQL-транзакцией. Связь проверяет точные tenant, runtime turn, process run, policy revision и root initiator из сохранённого process context. Отсутствующая или несовпадающая связь отклоняется закрыто.

Карточка внимания не содержит agent summary или prompt: её текст, props, payload hash и delivery id формирует сервер. Automation-запросы имеют отдельный `request_kind` и уникальность, поэтому generic MCP не может выбрать, переиспользовать или обновить их даже при одинаковых process run и idempotency key. Перед внешним POST reconciler сохраняет automation-specific claim с lease и монотонным confirmation-only fence; конкурентный callback или worker не получает второй claim. После единственной разрешённой POST-попытки потерянный ответ, ошибка PostgreSQL и перезапуск допускают только сверку по server-owned delivery id. Непрерывный ограниченный worker продвигает весь доступный backlog через `SKIP LOCKED`. Это восстановление принадлежит автоматизациям и не заменяет общий watchdog или callback outbox среды выполнения.

## Оркестрация процесса

- Менеджер является координатором процесса и запускает дочерних агентов только через MCP.
- Дочерний запуск содержит родителя, назначение, входные данные, контракт завершения и цель обратного вызова.
- Обратный вызов долговечен, идемпотентен и всегда возвращается менеджеру с исходным инициатором и назначением работы.
- Родительский процесс не считается завершенным, пока обязательные дочерние запуски и ручные проверки не завершены.
- Политика ошибки определяет повтор, замену исполнителя, пропуск либо передачу человеку.
- Перед межкомнатным запуском координатор проверяет каталог и карточку целевого чата; платформа проверяет relationship policy и наследует root initiator.
- Каждое делегирование независимой или security-проверки содержит три исхода замечания: `Merge blocker`, `MVP follow-up` и `Informational`.
- Обратный вызов проверки перечисляет исход каждого review thread; для `MVP follow-up` обязательны URL Issue и причина, по которой замечание не является blocker.
- Перед слиянием координатор проверяет GitHub GraphQL `reviewThreads` и не допускает unresolved или молча опущенные замечания.
- Успешный `mattermost_start_agent_thread` сначала создаёт дочерний тред, ставит запуск целевого агента в долговечную очередь и создаёт предусмотренные платформой событие аудита и служебное сообщение с признаком `notrigger`.
- Запущенная дочерняя сессия возвращает результат разрешенному координатору через `mattermost_return_to_requester`; обычный callback не упоминает инициатора. Ручной шлюз открывается через `mattermost_request_owner_attention`.

## Жизненный цикл ручной приемки

В `prototype-accelerated` жизненный цикл имеет вид:

`результат -> reviewer + security параллельно -> исправление blocker -> проверка менеджера -> merge -> post-merge reviewer + security -> backlog`.

Ежедневный `improver` отдельно обрабатывает merged PR без `improved`. Ни его
запуск, ни follow-up backlog не блокируют независимую реализацию без
`mvp-blocker`.

Ручная приемка владельца относится к конкретной версии результата. Изменение после OK отменяет согласование и требует повторного рецензирования и приемки, кроме заранее разрешенных механических изменений.

Открытый `OwnerAttentionRequest` привязан к треду хода, который запросил внимание. Следующее сообщение корневого инициатора в этом треде разрешает открытый запрос, продолжает тот же `ProcessRun` и сохраняет исходную ревизию политики. Ответ в одном треде не разрешает параллельные запросы внимания в других тредах процесса. Когда в процессе не осталось активных ходов и открытых запросов внимания, платформа переводит его в терминальное состояние.

Для запроса, созданного итогом автоматизации, решение разрешено только после сохранённых `mattermost_post_id` и server-owned `CreateAt` точной карточки. Transport переносит неизменяемый Mattermost `CreateAt` ответа до repository; ответ с `CreateAt`, не превышающим proof карточки, закрыто отклоняется. Допустимое решение сохраняет proof ответа и атомарно переводит точные `ScheduledRun` и occurrence в `succeeded`, задаёт `finished_at` и добавляет audit. Точный replay решения возвращает существующий результат; другой пользователь, канал, корневой тред или новый post после разрешения не создаёт повторного перехода. Гонка доставки и решения имеет два допустимых исхода: решение закрыто отклоняется до delivery и ordering proof либо выполняется после их фиксации.

Read-only история Control Center читается из PostgreSQL через версионированный OpenAPI endpoint и сгенерированный Vue-клиент. Она показывает как `waiting_owner/open`, так и сохранённое `succeeded/resolved`; обновление после решения идёт по тому же серверному пути, без production-зависимости от browser globals.

## Критерии приемки

- Две реплики планировщика создают один экземпляр расписания.
- Перезапуск не теряет следующий запуск и не создает повтор.
- Расписание применяет свежую `RuntimeRevision`.
- Запуск без чата работает без обсуждения.
- Менеджер запускает параллельные обсуждения и получает обратные вызовы.
- Занятый целевой агент сохраняет несколько запросов делегирования без потери инициаторов.
- Owner gate обязателен только когда его требует delivery policy или возникает новое решение, опасный deploy либо blocker.
- `improver` запускается одним ежедневным batch и помечает обработанные PR label `improved`.
- Перед слиянием каждый review thread имеет доказуемый исход, а отложенное замечание содержит URL Issue и причину отсрочки до разрешения thread.
- Открытые `mvp-follow-up` после обычного слияния попадают в отдельную ограниченную неблокирующую волну.
