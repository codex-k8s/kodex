# Смена PostgreSQL image и восстановление индексов

## Когда применять

Runbook обязателен при изменении `MATTERCODEX_POSTGRES_IMAGE` для существующего PVC, включая смену базового дистрибутива, реализации libc или версии правил сортировки. Даже при неизменной основной версии PostgreSQL новая collation может сделать существующие B-tree индексы логически поврежденными: поиск пропускает строки, уникальный индекс допускает дубли, а последующие `UPDATE` и `ON CONFLICT` завершаются `SQLSTATE 23505`.

Штатный установщик блокирует неявную смену image. Флаг `--allow-postgres-image-change` является подтверждением выполненного окна обслуживания, а не способом обойти проверки. Образ по умолчанию закреплен неизменяемым digest.

Справочные материалы PostgreSQL: [REINDEX](https://www.postgresql.org/docs/16/sql-reindex.html), [ALTER DATABASE](https://www.postgresql.org/docs/16/sql-alterdatabase.html), [изменение версии collation](https://www.postgresql.org/docs/16/sql-altercollation.html), [amcheck](https://www.postgresql.org/docs/16/amcheck.html).

## Предварительные условия

1. Опубликовать уведомление о технических работах.
2. Проверить в PostgreSQL отсутствие ходов `queued` и `running`, затем повторить проверку непосредственно перед остановкой сервисов.
3. Зафиксировать текущие image, digest, число реплик и состояние StatefulSet/Deployment.
4. Создать проверяемую резервную копию PostgreSQL вне PVC кластера.
5. Остановить все сервисы записи: `matter-codex-bot-service`, Mattermost и другие потребители этой БД. PostgreSQL остается запущенным.

Не удалять дубли автоматически. Сначала установить все внешние ключи, активные ходы, архивы сессии и актуальную строку. Разные строки с одинаковым бизнес-ключом могут содержать разные данные, которые требуется объединить в одной транзакции.

## Переключение image

Применить PostgreSQL отдельно через удаленный установщик:

```bash
scripts/remote/install-mattermost.sh \
  --env-file .env \
  --apply \
  --allow-postgres-image-change
```

При разрешенной смене image установщик ожидает PostgreSQL и запускает `deploy/k8s/mattermost/maintenance/verify-btree-indexes.sql` до применения манифеста Mattermost. Если `amcheck` обнаружил повреждение, установщик завершается, а сервисы записи должны остаться остановленными.

## Восстановление

1. Проверить уникальные индексы на фактические дубли и разрешить каждый конфликт с учетом внешних ключей и данных.
2. При остановленных writers перестроить пользовательские индексы текущей БД:

```sql
REINDEX DATABASE mattermost;
```

3. Только после успешного перестроения записать актуальную версию default collation:

```sql
ALTER DATABASE mattermost REFRESH COLLATION VERSION;
```

4. Повторно выполнить `verify-btree-indexes.sql`. Проверка должна завершиться без исключения.
5. Повторить установку с `--allow-postgres-image-change`: успешная проверка разблокирует применение Mattermost.
6. Развернуть `matter-codex-bot-service`, дождаться готовности и выполнить дымовые проверки.

`REINDEX DATABASE CONCURRENTLY` допустим для заранее спланированного обслуживания доступной БД, но работает дольше и не устраняет дубли уникальных ключей. При подтвержденном нарушении уникальности предпочтительно контролируемое окно без writers.

## Проверка после восстановления

- все B-tree индексы проходят `amcheck` с `heapallindexed=true`;
- запрос по каждому ранее конфликтующему уникальному ключу возвращает одну строку;
- Mattermost принимает и читает сообщения;
- bot-service готов на всех репликах;
- новый безопасный агентный ход запускается, завершается и возвращает callback;
- в логах PostgreSQL нет новых `duplicate key`, `item order invariant violated` и collation warning;
- StatefulSet использует ожидаемый digest, а не изменяемый tag.

## Откат

Не переключать старый image поверх данных, измененных под новой collation. Если восстановление индексов или проверка не завершились, оставить writers остановленными и восстановить проверенную резервную копию в отдельный PVC/кластер. Переключение приложения выполняется только после проверки индексов и прикладного smoke.
