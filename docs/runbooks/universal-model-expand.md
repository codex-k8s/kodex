# Расширяющая миграция универсальной модели

## Назначение

Этот runbook описывает проверяемое переключение конфигурационных записей с legacy `Project`, `Chat` и `AgentRole` на атомарный dual-write с `Workspace`, `Room`, `RoleDefinition`, `Agent`, `AgentAssignment`, `InstructionSet` и `InstructionVersion`.

Развертывание и изменение действующего кластера выполняет только уполномоченная роль в отдельном окне. Команды ниже не должны печатать DSN, токены, содержимое инструкций, внутренние или внешние идентификаторы.

## Предварительные условия

- сохранён точный SHA и дайджест N-1;
- подтверждена резервная копия и возможность исправления вперёд;
- для PostgreSQL используется migration owner, а приложение продолжает использовать отдельную runtime DML identity;
- конфигурационные записи через `/agents` и старые процессы остановлены на короткий quiesce;
- проверено отсутствие одновременно работающих N-1 legacy-only и N dual-write writers.

## Проверка миграции

1. Применить migrations новым экземпляром приложения без приёма конфигурационных mutations.
2. Подтвердить версию `000030` и отсутствие обязательных кодов preflight, перечисленных ниже.
3. Сравнить только агрегированные количества соответствий `Project`/`Workspace`, `Chat`/`Room`, `AgentRole`/`Agent`, workspace- и room-назначений.
4. Подтвердить, что каждый непустой legacy prompt получил V1, его сохранённый SHA-256 совпадает с пересчитанным, а пустые prompt не создали набор.
5. Проверить ограниченным runtime login запрет `UPDATE` и `DELETE` для `InstructionVersion`, запрет cross-scope ссылок и отсутствие прав DDL.
6. Включить один N writer и завершить quiesce.

## Ручной сценарий

В изолированной тестовой установке через `/agents`, без ввода внутренних идентификаторов:

1. создать рабочую область без GitHub account, owner и repository;
2. создать роль и конкретного агента с отдельной bot identity, OpenAI account и Markdown V1 размером не более 3000 UTF-8 байт;
3. создать комнату без repository и назначить агента;
4. убедиться, что карточка агента показывает номер версии, SHA-256 и владельца конфигурации, но не показывает содержимое секрета;
5. опубликовать V2 и подтвердить новую неизменяемую версию и обновлённую legacy-проекцию;
6. проверить отказ редактирования `managed_by=git`, затем явное отсоединение с сохранённым происхождением и событием аудита;
7. повторить существующий сценарий с repository и убедиться, что его callbacks и checkout не изменились.

Проверка точной версии инструкции в выполняющемся ходе, no-checkout pod и materialization `AGENTS.md` выполняется только после подключения Runtime-контракта.

## Ошибка preflight

Любой из следующих стабильных кодов означает, что migration ничего не изменила:

- `MCV30_DUPLICATE_MATTERMOST_TEAM_BINDINGS` — повторная привязка команды;
- `MCV30_DUPLICATE_MATTERMOST_CHANNEL_BINDINGS` — повторная привязка канала;
- `MCV30_CROSS_PROJECT_CHAT_PARTICIPANT` — участник комнаты принадлежит другому проекту;
- `MCV30_CROSS_PROJECT_BOT_IDENTITY` — bot identity принадлежит другому проекту;
- `MCV30_INSTRUCTION_MARKDOWN_TOO_LARGE` — legacy prompt превышает 65 536 UTF-8 байт.

Оставить записи остановленными, устранить противоречие офлайн по внутренним surrogate ID и повторить только обезличенную агрегатную проверку. Значения bindings, prompts и идентификаторов не помещаются в консоль, журналы, Issue или PR.

## Откат приложения

1. Остановить конфигурационные mutations.
2. Не выполнять `Down`: миграция forward-only, а история инструкций должна сохраниться.
3. Переключить трафик только на заранее проверенный exact N-1 SHA, совместимый с расширенной схемой.
4. Оставить universal editing только для чтения; N-1 продолжает читать общие данные и prompt из legacy-проекции.
5. Проверить legacy `/agents`, маршрутизацию и существующий repository-сценарий.
6. Исправить причину вперёд и повторить миграционный шлюз перед возвратом dual-write.

## Свидетельства

Зафиксировать SHA, дайджест, версию migrations, агрегированные результаты backfill, отказ forward-only `Down`, результат повторного `Up`, автоматические проверки и ручной сценарий. Отсутствие GitHub check runs указывается отдельно и не считается успешным CI.
