# Документация и инструкции агентов

## Метаданные

Активный документ имеет метаданные front matter со стабильными полями `id`, `title`, `type`, `status`, `owner`, `version` и датой `updated`.

Допустимые статусы: `draft`, `proposed`, `approved`, `superseded`, `archived`.

## Источник истины

- Поведение продукта - `docs/product`.
- Системная архитектура - `docs/architecture` и ADR.
- Владение доменами - `docs/domains`.
- Правила реализации - `docs/guides` и детальные инженерные руководства.
- Эксплуатация — `docs/operations` и пошаговые инструкции.
- Утверждённый UX-контракт и HTML-макеты — `docs/design`.

Документ не копирует правило другого раздела без ссылки и объяснения локального контекста.

## Изменения

- Существенное решение обновляет продуктовую, доменную и архитектурную документацию и ADR в одном цикле результата.
- Код не принимается, если он расходится с утвержденными документами без отдельного ADR.
- `improver` обновляет инструкции и руководства только отдельным проверяемым предложением в собственных Issue и PR.
- Результат `improver` проходит продуктовое, security и архитектурное review,
  затем human gate владельца; его callback сам по себе не разрешает слияние.
- Зависимая реализация разрешается только после принятия и слияния результата
  `improver`. Слияние не запускает новый `improver` рекурсивно.
- Удалённая реализация остаётся доступной в Git history; stale-документ не
  сохраняется в активном дереве только ради архива.

## Утверждения и доказательства

Документ явно различает три вида утверждений:

- **Фактическое текущее поведение** подтверждается ссылкой на код, данные или наблюдение и точным SHA либо датой. Нежелательное поведение может быть фактом, но не становится целевым контрактом.
- **Характеристическая проверка** зелёным тестом фиксирует фактическое поведение базовой версии. Её успешность доказывает воспроизводимость характеристики, а не приемлемость поведения.
- **Будущий целевой шлюз приёмки** описывает требуемое состояние после отдельной реализации. Пока реализация и проверка не выполнены, он помечается как планируемый контракт и не включается в список полученных доказательств.

Если одна оснастка сначала фиксирует текущий долг, а затем используется для целевого исправления, документ отдельно называет исход базовой версии, будущий ожидаемый исход, PR или Issue реализации и шлюз, после которого меняется ожидание. Зелёную характеристику запрещено выдавать за завершённую реализацию.

## Полнота изменения

- Резюме PR перечисляет все фактически изменённые файлы и назначение каждого из них, включая индексный файл, если он изменён.
- Выполненные проверки отделяются от планируемых и относятся к точному SHA ветки.
- Зависимости Issue указываются в тексте как `depends on`, `blocks`, `follows` или «основано на». Формальная dependency/sub-issue связь добавляется только при совпадении её реальной семантики; ссылка ради видимости не должна создавать ложную иерархию.
- Перед передачей результата выполняется проверка согласованности активных `docs/**`, русской проектной прозы и точности идентификаторов. Исторические документы не используются для переопределения активного решения.

## Язык

Проектные документы, Issues, PR и комментарии рецензирования по умолчанию пишутся на выбранной локали проекта или пользователя, если `AGENTS.md` не задает более конкретное правило. Комментарии в коде следуют тому же правилу. Идентификаторы кода и неизменяемые термины внешних API не переводятся искусственно.

В обычной русской прозе используются русские слова: владелец, менеджер, исполнитель, рецензент, рабочая область, комната, обсуждение, сессия, ход, поставщик, интеграция, согласование, расписание, очередь, обратный вызов, среда выполнения, развертывание, резервное копирование и восстановление.

Английская форма допустима:

- внутри идентификатора, команды, пути, конфигурации или фрагмента кода;
- при первом определении доменной сущности, например `RuntimeRevision`;
- для названия продукта, протокола или общепринятого формата: Mattermost, OpenAI Codex, MCP, OpenAPI, AsyncAPI, gRPC, S3;
- когда перевод изменит точный смысл внешнего контракта или канонического статуса.

Смесь вроде «owner запускает reviewer для review result» в проектной прозе запрещена. Правильная форма: «владелец запускает рецензента для проверки результата».

## Инструкции агентов

`InstructionSet` должен быть коротким индексом со ссылками на релевантные документы. Нельзя копировать весь корпус в промпт. Материализатор среды выполнения передает манифест и дает агенту читать нужные файлы.
