# Базовые проверки CI

## Активный прототипный профиль

До отдельного решения владельца о готовности прототипа функциональный PR
выполняет только быстрые применимые проверки:

- форматирование изменённых файлов;
- `git diff --check`;
- компиляцию/сборку затронутого кода;
- быстрый статический разбор, если он доступен без полного baseline;
- проверку сгенерированного diff при изменении исходного контракта;
- небольшие быстрые unit-тесты сложной чистой или security-critical логики.

Отсутствие полного test coverage, integration/E2E,
contract/deploy/render/lifecycle/oracle suites, container build, SBOM,
vulnerability scan и общего CI baseline в активной фазе прототипа не является
блокером и не должно становиться замечанием рецензента. Простому glue-коду не
нужен тест ради покрытия. PR перечисляет только фактически выполненные команды,
а будущий контур связывает с
[Issue #216](https://github.com/codex-k8s/matter-codex/issues/216).

## Будущий поддерживаемый baseline

После завершения прототипа и отдельного owner-approved запуска #216 профиль
может включить:

- форматирование Markdown и проверку ссылок;
- Go vet/staticcheck, unit и integration tests;
- frontend lint/typecheck/unit/build;
- contract compatibility и migration checks;
- Kubernetes/Helm render и schema checks;
- secret, dependency, license, SBOM и vulnerability scanning;
- OCI builds и поддерживаемые staging smoke/E2E.

Пункт становится обязательным только когда фактически работает, имеет
владельца, ограниченный бюджет времени, публичную точку входа и однозначные
исходы `PASS`/`FAIL`/`NOT RUN`.

## Основная ветка и выпуск

- однократная сборка и публикация неизменяемого дайджеста образа;
- подпись и происхождение;
- развертывание кандидатного окружения;
- дымовые и сквозные проверки;
- ручной допуск окружения;
- продвижение того же дайджеста через GitOps;
- проверка после развертывания;
- автоматическая остановка или откат нагрузки без локального состояния при неуспешном анализе.

## Сгенерированный код

CI запускает генераторы и требует чистое рабочее дерево. Изменение сгенерированного кода без изменения исходного контракта блокирует PR.

## PR только с документацией

Не запускает дорогие сборки образов без причины, но обязательно проверяет Markdown, внутренние ссылки, метаданные документов, запрещенные секреты и согласованность индексов.

## Интерпретация результатов

- Проверка считается успешной, только если она существовала для текущего SHA ветки, завершилась и имеет успешный результат.
- Пустой `statusCheckRollup`, отсутствие статусов коммита или сообщение `no checks reported` означают отсутствие GitHub `check runs`, а не зелёный CI.
- Локально выполненные команды перечисляются отдельно от проверок GitHub с командой, результатом и проверенным SHA.
- Если обязательные проверки GitHub не настроены или недоступны, шлюз фиксирует это как ограничение. Менеджер не подменяет ограничение успешным CI; владелец может явно принять его для конкретного низкорискового результата и точного SHA.
- Будущий шлюз приёмки, описанный в документации, не считается выполненной проверкой, пока соответствующий контур фактически не запущен и не приложено доказательство результата.
- Рецензент не создаёт finding только из-за отсутствия suite, отложенного
  активным профилем. Доказанный дефект production-кода или fail-open path
  остаётся блокером независимо от наличия теста.

## Ручная приемка

Успешный CI не заменяет приемку владельцем. Слияние выполняет менеджер после финального OK владельца, обратного вызова рецензента и проверки того же SHA.
