# Базовые проверки CI

## Активный профиль

Для web-first платформы действует `Web-first baseline`. Функциональный PR
выполняет все применимые поддерживаемые проверки:

- форматирование изменённых файлов;
- `git diff --check`;
- Go build/unit и disposable PostgreSQL component tests;
- frontend lint/typecheck/unit/build;
- Proto/OpenAPI/AsyncAPI validation и воспроизводимый codegen;
- web-only и optional-Mattermost Kubernetes render;
- Playwright contract/list check и browser E2E в разрешённой disposable среде;
- применимые security, secret, dependency, SBOM и vulnerability проверки.

Проверка имеет владельца, ограниченный бюджет, публичную точку входа и
однозначные исходы `PASS`/`FAIL`/`NOT RUN`. Недоступная разрешённая disposable
среда фиксируется как `NOT RUN`; ошибка существующей обязательной оснастки —
как `FAIL`.

## Основная ветка и выпуск

- однократная сборка и публикация неизменяемого дайджеста образа;
- подпись и происхождение;
- развертывание кандидатного окружения;
- дымовые и сквозные проверки;
- ручной допуск окружения;
- продвижение того же дайджеста через GitOps;
- проверка после развертывания;
- автоматическая остановка или откат нагрузки без локального состояния при неуспешном анализе.

## Сгенерированный код

CI запускает генераторы и требует чистое рабочее дерево. Изменение сгенерированного кода без изменения исходного контракта блокирует PR.

## PR только с документацией

Не запускает дорогие сборки образов без причины, но обязательно проверяет Markdown, внутренние ссылки, метаданные документов, запрещенные секреты и согласованность индексов.

## Интерпретация результатов

- Проверка считается успешной, только если она существовала для текущего SHA ветки, завершилась и имеет успешный результат.
- Пустой `statusCheckRollup`, отсутствие статусов коммита или сообщение `no checks reported` означают отсутствие GitHub `check runs`, а не зелёный CI.
- Локально выполненные команды перечисляются отдельно от проверок GitHub с командой, результатом и проверенным SHA.
- Если обязательные проверки GitHub не настроены или недоступны, шлюз фиксирует это как ограничение. Менеджер не подменяет ограничение успешным CI; владелец может явно принять его для конкретного низкорискового результата и точного SHA.
- Описанный, но не запущенный шлюз приёмки не считается выполненной проверкой.
- Доказанный дефект production-кода или fail-open path остаётся блокером
  независимо от наличия теста.

## Ручная приемка

Успешный CI не заменяет приемку владельцем. Слияние выполняет менеджер после финального OK владельца, обратного вызова рецензента и проверки того же SHA.
