# Эпики, волны и human gate

Большая разработка выполняется не россыпью технических подзадач, а
законченными волнами. Одна волна реализует один unit проекта одним большим PR,
проходит три независимых направления review и дает владельцу целостный
проверяемый результат.

## Нормативная единица поставки

Unit проекта - один самостоятельно развиваемый и поставляемый компонент:

- внутренний доменный сервис;
- внешний gateway;
- одна PWA;
- одна самостоятельно развертываемая job.

Один unit реализуется в одном Issue, одной ветке, одном изолированном worktree и
одном PR. PR может быть большим: ограничением служит связность компонента и
возможность проверить его целиком, а не количество строк.

Нельзя делить реализацию одного unit на PR по слоям: отдельно contracts,
repository, service, transport, observability или deploy. Такое дробление
создает промежуточные неработоспособные состояния и несколько источников
правды. Отдельный PR допустим только для заранее выделенной общей зависимости,
которая нужна нескольким параллельным unit и имеет собственного владельца.

## Иерархия

```text
Epic
├── Wave issue + PR: один сервис целиком
├── Wave issue + PR: один gateway целиком
├── Wave issue + PR: одна PWA целиком
└── Wave issue + PR: одна самостоятельно развертываемая job целиком
```

PR unit считается полным, когда в применимой части содержит:

- продуктовые сценарии, доменную документацию и acceptance criteria;
- исходные OpenAPI, Proto и AsyncAPI-контракты с codegen;
- доменную модель, use cases, services, ports и adapters;
- PostgreSQL migrations и repositories, Redis cache и object storage;
- синхронные клиенты, transactional outbox, NATS relay, durable inbox и
  consumers;
- composition root, runtime lifecycle и конфигурацию;
- authentication, authorization, tenant и replay boundaries;
- логи, метрики, traces, Sentry, dashboards и alerts;
- Dockerfile, Kubernetes base/overlays и secret names;
- README, runbook, rollback и ручные сценарии приемки.

Неприменимый пункт явно отмечается в PR с причиной. Placeholder вместо
обязательной части не считается завершением unit.

## Подготовка блока

Manager и architect:

1. связывают требования, сценарии, домены и acceptance;
2. определяют авторитетных владельцев данных;
3. составляют карту контрактов;
4. находят независимые волны;
5. фиксируют зависимости и порядок merge;
6. получают owner OK на состав параллельного блока.

Только после этого создаются подзадачи и запускаются исполнители.

## Реализация unit

1. Developer создает отдельный worktree, ветку и draft PR для связанного Issue.
2. До массовой реализации фиксируются сквозные сценарии, trust boundaries,
   contracts и границы unit.
3. Developer реализует полный scope unit, документацию, deploy и ручную
   проверку.
4. Developer выполняет самопроверку по `AGENT-DOC-001`, профильным гайдам и
   `GOV-DOC-003`.
5. PR переводится в состояние review только после завершения всего scope.

Пока активен профиль `Prototype`, самопроверка ограничена быстрыми
компиляцией/сборкой/форматированием/diff и небольшими unit-тестами сложной
чистой либо security-critical логики. Отсутствие полного покрытия,
integration/E2E/contract/deploy/render/lifecycle/oracle suites и общего
baseline не блокирует готовность прототипа к review. Полная стратегия вынесена
в [Issue #216](https://github.com/codex-k8s/matter-codex/issues/216).

Draft PR не передается на human gate как частично готовый результат. Если в
процессе обнаружена отсутствующая общая зависимость, developer либо реализует
ее в том же PR при узком влиянии, либо фиксирует блокирующую dependency Issue и
согласует порядок с manager.

## Три параллельных направления review

После завершения реализации manager одновременно запускает трех независимых
reviewer на одном и том же точном SHA. Каждый reviewer знает о двух
параллельных направлениях и не дублирует их без собственного доказанного
риска.

### Продуктовое review

Проверяет:

- соответствие договору, ТЗ, продуктовым и доменным документам;
- полноту пользовательских и операторских сценариев;
- роли, полномочия, состояния, переходы, ошибки и крайние случаи;
- согласованность внешних и внутренних контрактов со сценарием;
- ручную приемку и отсутствие необоснованного расширения scope.

Пробел документации не разрешает придумывать бизнес-правило. Reviewer
фиксирует противоречие или вопрос владельцу.

### Security review

Проверяет:

- trust boundaries, authentication, authorization и tenant isolation;
- mTLS, signed context, replay protection, idempotency и безопасные defaults;
- secrets, PII, audit, encryption, network policy и supply chain;
- fail-closed поведение, negative paths и последствия компрометации;
- безопасность migrations, cache, broker, object storage и deploy-профилей.

### Архитектурное review

Проверяет:

- соответствие структуре репозитория и границам слоев;
- целостность доменной модели, ports/adapters и composition root;
- согласованность Proto, OpenAPI, AsyncAPI, PostgreSQL, Redis и NATS;
- транзакции, outbox/inbox, ordering, retry и failure recovery;
- lifecycle, observability, эксплуатационную готовность и расширяемость;
- отсутствие дублирования общих primitives и скрытых источников правды.

Reviewer оставляет замечания с severity, файлом/строкой, достижимым сценарием
риска и ожидаемым инвариантом. Reviewer не вносит код в ветку developer и не
подменяет свое направление поверхностным просмотром только знакомых файлов.
В профиле `Prototype` reviewer не создаёт finding из-за отсутствия
отложенного полного test coverage или тяжёлой suite. Доказанный дефект
production path, противоречие требованиям или fail-open boundary остаётся
finding независимо от наличия теста.

## Цикл устранения замечаний

1. Developer получает все три review одного раунда.
2. Замечания группируются по общей причине; исправляются указанное место и все
   системные аналоги в коде, contracts, документации, конфигурации и deploy.
3. Developer выполняет быстрые применимые проверки активного профиля, пушит
   единый согласованный пакет исправлений и отвечает в каждом thread.
4. Все три reviewer одновременно проверяют новый точный SHA: собственные
   замечания, затронутое направление и отсутствие новых регрессий.
5. Thread закрывает его автор после проверки исправления. Статус `resolved`
   без проверки нового diff не является доказательством.
6. Если хотя бы одно направление нашло новое замечание, цикл повторяется с
   пункта 1.

Review завершено только когда:

- нет незакрытых review threads;
- каждый из трех reviewer явно подтвердил отсутствие замечаний по своему
  направлению на текущем SHA;
- фактический scope PR по-прежнему соответствует Issue;
- проверки активного профиля прошли на финальном SHA.

Нельзя отправлять PR владельцу между раундами review или считать отсутствие
ответа reviewer подтверждением.

## Human gate и слияние

После успешного review manager передает владельцу:

- ссылку на Issue и PR;
- точный финальный SHA;
- краткую карту реализованных сценариев;
- результаты трех направлений review;
- выполненные проверки и ручные шаги;
- известные остаточные риски и rollback.

Владелец выполняет приемку и либо дает отдельный OK на merge, либо возвращает
замечания. После замечаний владельца developer исправляет системные аналоги, а
все три reviewer выполняют новый параллельный раунд. Только после повторного
нулевого результата review и нового human gate PR может быть слит.

Нельзя бесконечно расширять PR улучшениями за пределами Issue. Новое
неблокирующее требование оформляется отдельным Issue, но подтвержденный дефект
текущего scope не переносится из PR только ради ускорения merge.

## Параллельность

Параллельные волны разрешены, если они:

- не редактируют одну машинную policy или shared library без согласованного
  владельца;
- опираются на уже утвержденные контракты;
- имеют разные worktree и ветки;
- не создают временные альтернативные источники истины;
- знают точный merge order.

Общий runtime или контракт сначала выделяется отдельной блокирующей волной либо
получает одного владельца. Параллельные агенты не копируют его в свои сервисы.

Manager не запускает зависимую волну только потому, что предыдущий PR открыт:
он проверяет фактический контракт и merge order. Независимые unit развиваются
параллельно, но каждый проходит собственные три review и human gate.
