# Пользовательские сценарии web-first Kodex

## UC-01. Первый полезный результат без интеграций

Владелец входит, видит готового Помощника Kodex, создаёт Проект «Продажи»,
ИИ-сотрудника «Аналитик лидов» и инструкции, запускает анализ загруженного CSV,
наблюдает live graph и скачивает итоговый отчёт. Ни Git, ни Kubernetes,
Mattermost, CRM или внешнее хранилище не требуются.

## UC-02. Создание ИИ-сотрудника через помощника

Владелец просит подготовить сотрудника для классификации обращений. Помощник
показывает plan preview: Project, Agent profile, instruction draft, capabilities
и role image. План полностью перечисляет создаваемые, изменяемые и удаляемые
объекты со всеми применяемыми параметрами; пользователь может отредактировать
инструкции в отдельном редакторе до подтверждения. После явного применения typed
operations создают обычные ресурсы; audit содержит пользователя и системного
помощника. Новый диалог и история доступны непосредственно в header drawer.

## UC-03. Собственное окружение роли

Администратор в редакторе с подсветкой создаёт Dockerfile `RoleImage` для
юридического сотрудника с PDF/OCR и офисными утилитами. `role-image-builder`
добавляет обязательный runtime contract, собирает образ через BuildKit и
публикует immutable revision после supply-chain checks. Администратор создаёт
три окружения: два pin-ят первый promoted digest, третье - второй; для каждого
выбирает env, secret refs, проверенные инструменты, resources, volumes, network
и workload RBAC profile. Новая image revision не меняет активные Sessions и
подключается к окружению только явным обновлением.

## UC-04. Многоагентный не-IT Процесс

Контент-координатор запускает Workflow: исследователь готовит факты, автор пишет
черновик, редактор проверяет. Делегирование идёт через типизированный MCP tool;
backend материализует nodes/edges и callbacks. Пользователь видит прогресс всех
ветвей и финальный пакет файлов.

## UC-05. IT Процесс как один из вариантов

Проект разработки подключает GitHub и Kubernetes definitions, выдаёт точные
grants агентам и запускает проверку релиза. Эти integrations не становятся
Project authority и могут быть отключены без изменения core модели.

## UC-06. Долговечное решение человека

Бухгалтерский Workflow просит согласовать платёж. Run переходит в
`WAITING_HUMAN`; Pod исполнителя может быть удалён. Владелец принимает решение в
web, Session восстанавливается и получает результат ровно один раз. Optional
Mattermost mirror после web-решения показывает stale/conflict readback. Decision
inbox до действия показывает Проект, Run, Session, инициатора, причину, эффект и
deadline; пользователь открывает detail panel и выбирает одну из разрешённых
операций.

## UC-07. Продолжение Session

После результата пользователь перетаскивает несколько файлов в composer и
добавляет уточнение в существующую Session. После upload и scan Control-plane
создаёт `AttachmentSet`, ставит новый FIFO Turn, создаёт свежую RuntimeRevision
и новый Pod того же promoted role image, сохраняя provider session и историю.
В workspace появляется read-only каталог с manifest, а platform-controlled
block сообщает агенту число и пути новых файлов даже при отсутствии файлового
цикла в пользовательском template. На графе остаётся одна Session node, а новый
Turn и его tool calls появляются внутри timeline.

## UC-08. Cancel и retry

Пользователь отменяет зависший Workflow. Все активные claims, gates и nodes
закрываются согласованно. Retry создаёт новую attempt и видимую lineage-связь,
не изменяя историю первой попытки.

## UC-09. Подключение CRM

Администратор создаёт connection, проверяет его и выдаёт capability только
агенту продаж. Credential остаётся в integration gateway. MCP invocation без
grant отклоняется; опасное изменение проходит approval policy и audit.

## UC-10. WebSocket reconnect

Клиент получил sequence N и потерял соединение. После reconnect gateway
авторизует Run, восстанавливает N+1…N+K из durable stream либо отдаёт новый
snapshot. Reducer не создаёт duplicate nodes и не откатывает новое состояние.
Маршрут не перезагружается, выбранная Session и viewport графа сохраняются, а
несохранённый ввод пользователя не исчезает.

## UC-11. Optional Mattermost

Организация отдельно включает notifications и result mirror, не включая inbound
или gate decisions. Outage адаптера виден как retryable delivery failure, а
успешный core Run, result и artifacts остаются доступными в Control Center.

## UC-12. Безопасное управление секретом

Администратор с правом изменения окружения создаёт секрет через Control Center.
`secret-broker` записывает новую immutable Kubernetes Secret version, а UI после
ответа показывает только короткий `display_hint`. Для повторного просмотра
администратор нажимает специальную кнопку, проходит свежую OIDC re-auth и
получает одноразовый ответ, который не сохраняется в браузере. Пользователь без
`secret.reveal` видит только metadata; попытка раскрыть foreign Project secret
закрыто отклоняется. Ротация создаёт новую version без изменения истории
предыдущих RuntimeRevision.

## UC-13. Шаблон инструкций и доступные инструменты

Владелец открывает ИИ-сотрудника и редактирует инструкции как Markdown-шаблон.
Каталог показывает типизированные переменные текущих scopes и коллекцию
инструментов, реально найденных в image и разрешённых environment. Владелец
добавляет `range` по `tools` и `.input.files`, выполняет validate и preview на
безопасном контексте и публикует immutable revision. Неизвестная переменная,
запрещённая функция или попытка сослаться на secret не проходит validation.

## UC-14. Вложения в разных точках работы

Пользователь добавляет любое число файлов через drag-and-drop в диалог Kodex,
новый Run, вход Process, продолжение Session и комментарий Human Gate. Общий
composer показывает очередь, progress, retry и удаление до отправки; большие
наборы передаются bounded chunks и batches. Существующий Project file
прикрепляется по immutable revision без копирования body. После отправки каждый
agent получает только разрешённый snapshot, а template может вывести отдельные
descriptors либо общий каталог, количество и manifest.

## UC-15. Корзина и удаление файла

Пользователь удаляет файл из workspace и подтверждает действие. Artifact
исчезает из обычных списков, перестаёт выдаваться новым Turns и в течение 30
дней доступен в корзине для восстановления. Если файл уже materialized в
работающем Pod, UI показывает затронутый Run и предлагает отменить его, но не
изменяет snapshot скрыто. Владелец может восстановить файл, удалить выбранные
объекты безвозвратно или очистить корзину; purge удаляет точную S3 version и
оставляет только минимальный audit tombstone.

## UC-16. Наблюдение за многоагентным Run

Владелец открывает Run на full-bleed canvas. Каждая node соответствует одной
логической Session, поэтому три независимых запуска одного сотрудника видны как
три nodes, а retries и continuations одной Session остаются в её timeline.
Состояния nodes и edges объясняет legend. По клику пользователь видит inspector,
открывает activity drawer с сообщениями и нормализованными tool calls из
`codex exec --json`, а в detail dialog с отдельным permission просматривает
параметры запуска и полностью материализованные prompts. Pan, zoom и fit не
сбрасываются при realtime reconnect.

## UC-17. Точечный доступ сотрудника организации

OIDC group назначает пользователю базовую роль участника. Администратор выдаёт
instance-level binding: разрешает видеть один Проект и запускать только
сотрудника «Аналитик», но не изменять его инструкции, окружение, secrets и не
запускать остальных сотрудников. Экран effective access показывает роль,
binding и итоговый набор полномочий. Попытка самостоятельно выдать более широкую
роль или открыть full prompt, secret reveal либо чужой Artifact отклоняется.

## UC-18. Аватар и адаптивное редактирование сотрудника

Пользователь загружает изображение сотрудника, обрезает его и сохраняет новую
immutable revision в S3. После удаления изображения UI показывает generated
fallback. На широком экране редакторы инструкций и runtime используют всю
доступную ширину и подходящий semantic dialog, а на mobile остаются доступны с
клавиатуры без горизонтального overflow.
