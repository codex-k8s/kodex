# Бизнес-процессы MatterCodex

## BP-SETUP-001. Подготовка рабочей области

1. Владелец создает или импортирует `Organization`.
2. Создает `Workspace`; система создает или привязывает команду Mattermost.
3. Подключает учетные записи поставщиков моделей и интеграции.
4. Создает `RoleDefinition` и конкретных агентов.
5. Назначает агентам интеграции, учетные записи, инструкции и профили среды выполнения.
6. Создает комнаты и добавляет участников.
7. Проверяет готовность без просмотра исходных значений секретов.

## BP-CHAT-001. Интерактивная работа с агентом

1. Пользователь пишет сообщение верхнего уровня или ответ.
2. При отсутствии явного адресата выбирается агент комнаты или обсуждения по умолчанию.
3. Вложения сообщения проходят прием, проверку и материализацию.
4. Система подтверждает прием сообщения и ставит ход в долговечную очередь.
5. Контроллер среды выполнения вычисляет свежую конфигурацию, запускает либо продолжает сессию.
6. Агент обновляет ход работы отдельными сообщениями с признаком `notrigger`.
7. Финальный ответ и файлы публикуются от учетной записи бота агента.

## BP-RESULT-001. Доработка результата через ручную приемку

Шлюз ручной приемки применяется к завершенному типу результата, например:

- структуре сервиса и границам модулей;
- OpenAPI/gRPC/AsyncAPI контрактам;
- доменным моделям, репозиториям, сервисам и обработчикам;
- UX-макетам и описанию экранов;
- эксплуатационной инструкции, развертыванию или отчету.

Порядок:

1. Менеджер формулирует один проверяемый результат и критерии приемки.
2. Исполнитель создает результат.
3. В `prototype-accelerated` независимый reviewer и security выполняют по одному параллельному проходу и классифицируют каждое замечание как `Merge blocker`, `MVP follow-up` или `Informational`.
4. Исполнитель устраняет все `Merge blocker` одним циклом; авторы blocker проверяют собственные находки.
5. Для `MVP follow-up` автор до разрешения thread создаёт Issue с labels `mvp-follow-up` и предметным label, отвечает URL Issue и причиной безопасной отсрочки.
6. Менеджер проверяет точный SHA, фактические CI/checks, GraphQL `reviewThreads` и отсутствие молча опущенных замечаний.
7. Если границы волны заранее одобрены, менеджер выполняет merge без отдельного owner gate; иначе открывает ручной шлюз.
8. После merge отдельные reviewer и security проверяют merge commit и создают `mvp-blocker` либо `mvp-follow-up` Issues.
9. Независимые волны продолжаются, если post-merge аудит не создал `mvp-blocker`.
10. Один раз вечером директор запускает один improver batch по merged PR без `improved`; обработанные PR получают label.

Ни менеджер, ни рецензент не должны трактовать отсутствие ответа владельца как автоматическое одобрение.

## BP-DELEGATE-001. Делегирование агенту

1. Агент вызывает другого агента только через инструмент делегирования MCP.
2. Перед межкомнатным запуском координатор вызывает `mattermost_list_chats(target_agent)`, выбирает чат по назначению и типу и проверяет через `mattermost_get_chat(chat)` его `work_policy`, репозитории и назначение целевой роли.
3. Успешный `mattermost_start_agent_thread` сначала идемпотентно создаёт дочерний тред, ставит запуск целевого агента в долговечную очередь и создаёт предусмотренные платформой событие аудита и служебное сообщение с признаком `notrigger`.
4. Если целевой агент занят в этой области сессии, поставленный запуск остаётся в очереди; совместимые запросы могут быть объединены с указанием каждого инициатора и его промпта.
5. Запущенная дочерняя сессия возвращает результат разрешенному координатору через долговечный callback без упоминания человека.
6. По завершении дочерний агент отправляет долговечный обратный вызов через `mattermost_return_to_requester`; он содержит самодостаточный результат и рекомендуемое продолжение, а платформа связывает его с исходным запуском и обеими ветками обсуждения.
7. Разрешенный координатор принимает обратный вызов и решает, запускать ли следующего агента, дождаться ли других результатов, вернуть ли работу на исправление или отдельно открыть шлюз внимания инициатора через `mattermost_request_owner_attention`.
8. Менеджер не публикует через `mattermost_post_thread_update` в уже созданный дочерний тред: текущий инструмент работает только с текущим тредом вызывающей сессии.
9. Обычные упоминания Mattermost от учетных записей ботов не запускают агентов.

## BP-PAR-001. Параллельные волны

1. Менеджер создает отдельное обсуждение на каждую независимую инициативу.
2. Для каждого обсуждения задаются цель, роли, интеграции, репозитории, критерии и шлюз ручной приемки.
3. Дочерние запуски выполняются независимо и не смешивают историю сессий.
4. Менеджер получает обратные вызовы и агрегирует состояние.
5. Владелец принимает каждый тип результата отдельно либо согласованным групповым шлюзом.

## BP-FOLLOWUP-001. Post-merge аудит и backlog MVP

1. После merge отдельные reviewer и security проверяют точный merge commit.
2. Срочные находки получают `mvp-blocker`, остальные — `mvp-follow-up` и предметный label; Issue связывается с исходным PR и доказательством.
3. `mvp-blocker` открывает отдельный hotfix и останавливает только затронутую волну.
4. Директор выбирает `mvp-follow-up` в свободные слоты по риску и совместимости, а не запускает все находки после каждого merge.
5. Результаты оформляются отдельными PR и не расширяют задним числом границы уже слитого результата.
6. Ежедневный improver анализирует эти Issues вместе с PR без `improved`, но не исправляет продуктовый долг вместо исполнителя.

## BP-SCHED-001. Периодический запуск агента

1. Пользователь создает `AutomationSchedule` через UI, выбирая агента или процесс, расписание, часовой пояс и промпт.
2. Планировщик создает уникальный экземпляр запуска в PostgreSQL.
3. Запуск получает актуальные учетную запись, интеграции, переменные окружения, конфигурацию и инструкции.
4. Агент выполняется без привязки к чату либо в связанном обсуждении Mattermost.
5. При `no_action` политика уведомлений может не создавать сообщение.
6. При обнаружении работы агент через MCP создает обсуждение или запускает другого агента.
7. Результат, файлы, дочерние запуски и ошибки сохраняются в аудите и истории.

## BP-ART-001. Обработка вложений и результатов

1. Входной файл скачивается из Mattermost или источника интеграции.
2. Выполняются нормализация, хеширование, проверки политик и поиск вредоносного содержимого.
3. Основной объект сохраняется в S3-совместимом хранилище.
4. Файл материализуется только для чтения во входном каталоге рабочей области сессии.
5. Промпт получает манифест с именем, типом, размером, контрольной суммой и локальным путем.
6. Агент создает результат только в разрешенном выходном каталоге.
7. `publish_artifact` проверяет файл, сохраняет артефакт и публикует его в обсуждении.

## BP-APR-001. Опасное интеграционное действие

1. Агент вызывает инструмент MCP.
2. Шлюз интеграций проверяет `AgentGrant` и политику риска.
3. Для действия, требующего согласования, создается `ApprovalRequest`.
4. Человек получает Mattermost/Control Center карточку с безопасным описанием действия.
5. MCP возвращает агенту `pending`; ход завершается, архив сессии сохраняется, а pod можно удалить по TTL.
6. После согласования операция выполняется идемпотентно; после отклонения или истечения срока сохраняется структурированный отказ.
7. Результат создает ход продолжения, который восстанавливает ту же сессию Codex через `resume`.
8. Запрос, решение, результат выполнения и продолжение сохраняются в аудите.

## BP-IMPR-001. Непрерывное улучшение инструкций

1. `Improver` запускается директором один раз вечером по merged PR без label `improved` либо как отдельная работа по явному материальному замечанию.
2. Собирает комментарии рецензирования, замечания владельца, неуспешные запуски и повторяющиеся дефекты.
3. Группирует причины, не копируя чувствительные данные.
4. Готовит изменения `InstructionSet`, руководств, шаблонов ролей или процессов.
5. Изменения оформляются отдельным Issue и PR и проходят quality policy текущего режима.
6. Обработка PR завершается добавлением label `improved`, даже если изменение инструкций не потребовалось.
7. Результат `improver` не блокирует независимую реализацию; `mvp-blocker` оформляется отдельной Issue и останавливает только затронутую волну.
8. Слияние собственного PR не создаёт рекурсивный запуск; следующий запуск выполняется очередным ежедневным batch.
