# Самостоятельный срок согласования результата этапа

Задача: [#1869](https://github.com/codex-k8s/kodex/issues/1869),
эпик [#1830](https://github.com/codex-k8s/kodex/issues/1830).
До изменения публичные `expiresAt` и `EXPIRED` не имели самостоятельного
исполняемого срока Gate. Workflow timeout закрывал Gate как `CANCELLED`.

## Граница поведения

Владелец может задать `approvalTimeoutSeconds` от 1 до 604800 только у этапа
с `humanGate=true`. Отсутствие поля сохраняет прежнее поведение. Нет общего
значения по умолчанию, переноса срока на старые Gate или изменения часов.
Это отдельный срок ожидания после завершения этапа; `timeoutSeconds` процесса
и этапа отсчитывается по прежним правилам с первого claim и действует независимо.

Политика включается в immutable опубликованную версию workflow. При завершении
точного этапа CP читает её через проверенные lease, RuntimeRevision, run/node,
agent и published version. `created_at` и `expires_at` Gate вычисляются из одного
момента времени PostgreSQL. Последующая публикация или редактирование draft
не меняет начатое ожидание. Отсутствующий срок хранится как NULL.

Истечение обычного Gate результата завершает корень `FAILED` с причиной
`OWNER_GATE_EXPIRED`, точный Gate — `EXPIRED`, его узел — `FAILED`.
При выборе причины учитываются действующие часы всех параллельных этапов
корня и его предков; timeout относится к фактическому execution node. Среди
открытых Gate корня проверяется самый ранний срок, независимо от того, какой
Gate указан в поздней команде владельца. HTTP проверяет диапазон целого числа
до сужения к int32, включая значения, способные переполниться в допустимый срок.

Сервер не присваивает человеку решение: `decision` и `resolved_by` остаются NULL.
Другие открытые Gate этого закрываемого графа отменяются. Все прежние leases,
turns, invocations, доставки и незапущенные узлы закрываются в одной транзакции
через существующий terminal path. Начатый внешний WRITE сохраняет
`UNKNOWN_OUTCOME`, а не получает ложный успешный результат или повтор.

Этот профиль относится к обычным workflow Gate результата. Срок integration
approval и его отрицательное продолжение остаются отдельным непроверенным
контуром; этот unit не объявляет их реализованными. Также он не реализует
серверный DAG #1836 и не возобновляет остановленные пути #1838/#1848.

## Сквозная карта и полномочия

| Инициатор и полномочия | Вход и владелец состояния | Результат и потребитель |
| --- | --- | --- |
| Владелец с правом менять workflow | Прежний HTTP create/update draft → gateway mapping → прежний CP RPC → entity validation → published spec/digest | Политика доступна через HTTP, strict workflow catalog и PWA; поле не выдаёт runtime grant |
| Проверенный runtime worker | Прежний CompleteExecution, точные lease/fence/generation и опубликованный этап | Один OPEN Gate с immutable сроком; `OWNER_GATE_OPENED`, owner GET и realtime |
| Авторизованный runtime-controller | Прежний ClaimExecution, ограниченная выборка организации; повторная проверка под project/root/gate locks | Один terminal graph и `OWNER_GATE_RESOLVED`, точные run/node events, audit и command receipt |
| Владелец с правом ResolveGate | Прежний HTTP resolve → CP command; fresh authority и receipt replay до проверки срока | Позднее решение не исполняется; истечение фиксируется до возврата AlreadyResolved. Повтор той же команды читает прежнюю квитанцию |

Отдельного RPC, worker, listener, grant, runner ABI, Secret или глобального
флага не добавляется. Тик принадлежит существующему runtime claim loop.
SQL failure возвращает закрытый отказ и не считается отсутствием работы.

## Матрица жизненного цикла

| Состояние/событие | Авторитетный исход |
| --- | --- |
| OPEN без срока | Прежнее ожидание; никакого нового события |
| OPEN до срока | `expiresAt` виден; продолжения и внешнего эффекта нет |
| Срок Gate наступил первым | Один EXPIRED и FAILED root; закрытие всех зависимых полномочий в той же транзакции |
| Срок исполнения наступил раньше либо одновременно | Прежние RUNTIME_TIMEOUT и CANCELLED Gate; причины не переименовываются |
| APPROVE/REJECT/CANCEL уже победил под блокировкой | Решение сохраняется; последующий poll не истекает закрытый Gate |
| Поздний APPROVE | Терминальный исход фиксируется; эффект не выполняется; replay остаётся отказом |
| Чужой проект, неверная authority | Отказ до изменения; payload не назначает владельца |
| Stale version до истечения | Прежний OCC-отказ; разрешённый владелец не подменяет версию |
| Retry/cancel/delete terminal graph | Прежний специализированный lifecycle; закрытый Gate повторно не открывается |
| Новый draft/published revision | Старые Gate и RuntimeRevision сохраняют pins |

## Проверка и поставка

Поддерживаемая PostgreSQL-проверка — `make test-control-plane-postgres` с
`TestOwnerGateExpiryComponent`. Она создаёт disposable данные штатными owner
командами, действительно публикует workflow, исполняет claim/delegation/completion,
ждёт реального времени и проверяет исход через owner read. Запись готового
бизнес-состояния или часов в SQL не используется. Результат любого запуска
фиксируется отдельно с точным SHA; наличие теста не означает PASS.

Ручная проверка на staging: в отдельном QA-процессе задать срок согласования
короче срока этапа, выполнить его сотрудником, увидеть OPEN и `expiresAt`,
дождаться EXPIRED и убедиться, что следующий этап не запущен. Повторить с
ранним approve и с поздним approve, перезагрузкой браузера и адресным рестартом.
Модельные и внешние действия остаются в исходных пределах QA.

Штатный `tools/release/control-plane-migration.mjs` принимает закрытый профиль
`--profile owner-gate-expiry`: plan → check → stop → apply → inspect → resume.
Он сохраняет прежние UID/версии, immutable image/publication pins, stop/join и
единственный журнал эффектов. Precondition требует предыдущую Goose-версию
`20261025000200`, отсутствие колонки и активных работ, включая WAITING_HUMAN.
Read-only postcondition проверяет точные CHECK, nullable колонку, индекс,
неизменяемость срока и execute-права. Тот же SQL выполняется в PostgreSQL suite.
Неизвестный исход требует inspect, а не повторного apply с новым планом.

Миграция `20261026000100` выполняется штатным migrator через owner-role до
поставки нового CP: новые owner read всегда читают колонку. Она добавляет nullable
поле и forward-only ограничения;
старые строки не получают срок. До первой публикации политики со сроком все
реплики CP, API, runtime-controller и PWA должны обслуживать согласованные
новые версии. Runtime-controller обязан обновить strict catalog decoder.
Старый CP способен игнорировать новое поле, старый RC отклоняет его; смешанный
активированный контур непригоден для приёмки.

Возврат до активации новой политики допускает прежние приложения при сохранённой
расширенной схеме. После публикации первого срока возврат допускает только
совместимые с этим полем версии; удалять сроки, EXPIRED или исторические
квитанции ради rollback нельзя. Для такого возврата нужен исправляющий
forward-compatible образ. Полный immutable релиз подтверждается отдельно.
