# Назначение

Диагностический manifest `tools/dev/runtime-browser-control-1952.yaml` относится
к [#1952](https://github.com/codex-k8s/kodex/issues/1952). Он проверяет тот же
закреплённый role image и UID 10002 в отдельном Pod без модели,
credentials, PVC, Secret и host mounts. Запуск не является приёмкой сотрудника
или исправлением дефекта. Успех только локализует различие между Pod и
песочницей Codex; отказ требует анализа фактического stderr и termination.

Начальный контроль вне Codex sandbox на `09e58115a` открыл страницу за 3715 мс
с `chromiumSandbox: true`; Pod и NetworkPolicy удалены по точным UID.
Текущая ревизия запускает две короткие команды `codex sandbox` без модели и
авторизации: с `/proc = deny` и `/proc = read`. Это дифференциальная диагностика
только пустого Pod. Профиль сотрудников и права действующей платформы не меняются;
результат `read` не разрешает предоставлять такое право настоящему сотруднику.
Временные CODEX_HOME содержат только создаваемую диагностическую конфигурацию.
Только одно изменение правила `/proc` различает два профиля; каждый получает
собственные временные HOME и каталоги Codex, но одинаковую команду браузера.

На `95c52490a` обе команды вернули exit 1 без stdout/stderr. Этот результат
не доказывает даже вход в браузерную команду. Следующий контроль сначала
проверяет версию CLI и запись фиксированного marker обычным Node внутри
каждой песочницы. Только подтверждённый marker допускает запуск Chromium;
он также пишет отдельное свидетельство начала и результата во временный файл.
Читаются лишь два известных пути локального диагностического лога нового,
пустого CODEX_HOME с пределом 16 KiB; действующие provider logs не затрагиваются.
Чтение ограничено размером буфера и не следует по символьным ссылкам. Пустой
либо частично записанный marker после SIGKILL отмечается отдельно и не скрывает
код завершения, сигнал и timeout дочернего процесса.

QA самой платформы уже воспроизвёл SIGTRAP двумя запусками Playwright с
`chromiumSandbox: true`. Штатный Dockerfile smoke использует default этого
параметра, который равен false согласно Context7 `/microsoft/playwright`,
`docs/src/api/params.md`; эти проверки не эквивалентны.

# Полученное свидетельство

На `750d826853de08f4e1e2ebb6eb8fd16bc11ebb61` обе Node-команды записали
marker и завершились с exit 0. Chromium в обоих профилях завершился SIGTRAP
через 376 и 386 мс. При диагностическом `/proc = read` журнал дополнительно
показал `setsockopt: Operation not permitted`. stdout вложенной Node-команды
был пуст даже при подтверждённой записи marker; отсутствие stdout не доказывает
отсутствие исполнения. Pod и NetworkPolicy удалены с exact UID readback.

В [исходниках Codex rust-v0.160.0](https://raw.githubusercontent.com/openai/codex/rust-v0.160.0/codex-rs/linux-sandbox/src/landlock.rs)
режим Restricted запрещает `setsockopt` без проверки типа сокета. Наблюдение
согласуется с [upstream #47452](https://github.com/openai/codex/issues/47452),
но не заменяет трассировку фактического фильтра и аттестацию binary-to-source.
Открытие `/proc` не исправило браузер. Поддержанный исправленный sandbox либо
отдельный ограниченный browser worker ещё не реализован; браузерный путь
сотрудника остаётся FAIL. Обычный smoke образа вне Codex sandbox не подтверждает
готовность браузерного инструмента сотрудника.

# Порядок оператора

## Независимая гипотеза managed proxy

После завершения прежнего Restricted-пути добавлена отдельная оснастка
`tools/dev/runtime-browser-proxy-control-1952.yaml`. Она не повторяет сравнение
`/proc`: сохраняет `/proc = deny` и проверяет штатный managed proxy Codex
с пустым списком разрешённых доменов. По официальной
[документации permissions](https://learn.chatgpt.com/docs/permissions#network-permissions)
профиль сети сам по себе не включает proxy; требуется `features.network_proxy`
либо управляемая конфигурация. В текущем producer Kodex такой feature не записан.
Это основание проверить отдельный путь, а не доказательство причины SIGTRAP
или разрешение изменить действующие полномочия сотрудников.

Оснастка включает proxy только внутри нового пустого Pod и оставляет
`allow_upstream_proxy`, SOCKS, local binding и общий доступ к Unix sockets
выключенными. Отдельная NetworkPolicy запрещает весь ingress/egress; её точный
selector не совпадает с первой оснасткой. До Chromium обязательны три факта:
bytes несекретного файла-canary недоступны внутри sandbox; адрес локального proxy
действительно передан дочернему процессу; запросы запрещённого домена и локального
адреса получили именно HTTP403 от proxy. Ошибка DNS, timeout, отсутствие proxy
или только запрет Kubernetes не заменяют доказательство. Маскирование canary
пустым файлом учитывается отдельно от `EACCES`/`EPERM`.

Только после этих проверок запускается `chromiumSandbox: true`, локальный DOM,
чтение title и закрытие браузера. Модель, реальные credentials и внешний сервис
не вызываются. Общая команда ограничена25секундами, Pod —45секундами.
При неизвестном исходе дочерних процессов файлы не удаляются из-под них:
cleanup подтверждается исчезновением exact Pod UID, затем удалением policy.
Все остальные preflight, server dry-run, UID/readback и rollback требования ниже
применяются к имени `qa-browser-proxy-control-1952`.

Этот контроль ещё не выполнен. Даже его успех не разрешает заменить runtime
политику: нужны отдельные проверки всех прежних сетевых режимов, model/runtime
boundary, локального HTTP сервиса и реального QA-сотрудника. Отказы первого
Restricted-пути сохраняются; общего вывода о готовности браузера пока нет.

## Создание и удаление точных ресурсов

1. Проверить текущие cluster, namespace и node UID штатным
   `staging-capacity-preflight.py`, бюджет 256 MiB и резерв 5 GiB. Сохранить
   приватный receipt. Проверить отсутствие обоих ресурсов manifest; неизвестное
   существующее состояние запрещает create или повтор.
2. Проверить SHA, чистоту worktree, digest образа в manifest и его наличие
   на указанном staging node. `imagePullPolicy: Never` запрещает загрузку образа.
   Сверить отсутствие активного изменения этих ресурсов другим оператором.
3. Выполнить server dry-run с явным `--context k3d-kodex`. Создать сначала
   NetworkPolicy и проверить exact spec/UID, затем Pod. В Pod нет секретов и
   service-account token. Отдельная NetworkPolicy запрещает ingress/egress;
   её добавление не меняет правила других Pod. Проверить весь набор namespace
   policies, выбирающих диагностический Pod: ни одна не должна разрешать ingress
   или egress. Общая default-deny policy допустима; отдельная запрещающая policy
   не отменяет разрешения из других выбирающих policies.
4. Сохранить assigned UID и фактический spec обоих ресурсов. Ожидать terminal
   не более 60 секунд, читать только журнал `browser-control` и termination.
   Browser открывает локальный DOM; внешние URL и `--no-sandbox` запрещены.
   Проверка Node ограничена пятью секундами, браузерная команда — пятнадцатью;
   общий Pod deadline остаётся 45 секунд. Ошибка запуска
   оболочки отличается от наблюдённого отказа Chromium. Общий exit 0 говорит
   лишь о завершённом сборе двух результатов, а не об их успешности.
   Timeout/OOM/image absence/API error остаются отдельными отказами контроля.
5. Удалить только exact созданные UID: сначала Pod и дождаться NotFound, затем
   NetworkPolicy. При неизвестном исходе не повторять create; перечитать ресурсы.
   Не менять seccomp, AppArmor, user namespace policy, kernel или firewall хоста.

# Границы и возврат

Manifest не является workload платформы и не получает runtime grant. Для
сопоставимости container seccomp повторяет существующий provider-runtime;
остальные ограничения Pod сохраняются: non-root, все capabilities удалены,
no-new-privileges и read-only root. Ограничены CPU, память, временный диск и
время. Контроль не читает действующий рабочий каталог сотрудника.

Возврат — подтверждённое удаление двух созданных объектов с UID preconditions.
Образы, registry, приложения и принятые артефакты не меняются. Даже при
`titleOK: true` требуется отдельная проверка реального сотрудника после
исправления; два предыдущих FAIL не заменяются результатом этого контроля.
