# Шлюзы ручной приемки по типам результата

## Принцип

Шлюз ручной приемки ставится на законченный и проверяемый тип результата, а не на каждую внутреннюю задачу агента.

Примеры одного шлюза:

- границы сервисов и структура каталогов;
- контракты OpenAPI, gRPC и AsyncAPI;
- доменные модели, репозитории, сервисы и обработчики;
- пользовательский сценарий и набор экранов;
- контракт возможности интеграции и согласований;
- топология развертывания и эксплуатационная инструкция;
- проект резервного копирования и восстановления;
- готовый функциональный срез со сквозными проверками.

## Обязательный цикл

```text
Менеджер определяет результат
  -> Исполнитель создает версию N
  -> Проход рецензента 1
  -> Исполнитель исправляет замечания
  -> Проход рецензента 2
  -> Исполнитель исправляет замечания
  -> Необязательный проход рецензента 3
  -> Менеджер проверяет готовность
  -> Приемка владельцем 1
      -> есть замечания: исполнитель исправляет -> полная проверка -> повторная приемка
      -> предварительный OK: финальная проверка -> финальный OK владельца
  -> Рецензент возвращает менеджеру итоговые доказательства
  -> Менеджер сливает и публикует обычный результат
  -> Менеджер запускает Improver
  -> Improver создаёт отдельные Issue и PR улучшения процесса
  -> Независимое полное рецензирование и ручные шлюзы владельца
  -> Менеджер сливает принятый результат Improver
  -> Исходный цикл Improver завершён; зависимая реализация разрешена
```

Владелец может явно сократить число проходов рецензирования для низкорискового результата. По умолчанию менеджер планирует 2-3 прохода до первой приемки.

Обычным здесь называется результат, который не создан в рамках текущего цикла `improver`. Слияние результата `improver` является терминальным событием исходного цикла и не возвращает процесс к автоматическому запуску `improver`. Новый цикл создаётся только отдельной явно обоснованной работой по новому материальному замечанию.

## Ответственность

### Менеджер

- определяет один результат и критерии приемки;
- выбирает исполнителей, рецензентов и отдельные цели проверки;
- не передает владельцу сырой или непроверенный результат;
- отслеживает обратные вызовы дочерних работ и блокировки;
- не считает молчание одобрением;
- после финального OK владельца получает отдельный обратный вызов рецензента по проверке после OK, проверяет актуальный SHA, фактическое состояние CI и проверок GitHub и закрытые замечания, затем выполняет слияние с защитой от смены SHA ветки;
- после слияния обычного принятого результата запускает `improver` через MCP;
- не считает обратный вызов `improver` разрешением на зависимую реализацию, а проводит его отдельный результат через полный цикл рецензирования и ручной приемки;
- только сам сливает принятый результат `improver`, после чего разрешает следующую массовую зависимую реализацию;
- не запускает новый `improver` автоматически из-за слияния PR улучшения процесса.

### Исполнитель

- создает результат и проверяемые доказательства;
- отвечает на каждое требующее действия замечание;
- не закрывает обсуждение рецензирования без фактического исправления или обоснования;
- после замечаний владельца не меняет границы работы скрыто.

### Рецензент

- проверяет результат против документации и критериев, а не вкусовых предпочтений;
- разделяет блокирующие и неблокирующие замечания;
- после любого изменения SHA повторно проверяет весь результат и затронутый контракт, а не только последние изменения;
- проверяет треды GitHub `reviewThreads` с учетом `resolved`-статуса и новых ответов, а не только плоский список комментариев;
- привязывает `APPROVE` и обратный вызов к точным SHA ветки и базовой ветке;
- возвращает менеджеру обратный вызов с выводами, закрытыми замечаниями, проверенным SHA и фактическим состоянием CI и проверок GitHub;
- не выполняет слияние и не выбирает следующий этап процесса.

### Владелец

- принимает законченную версию результата;
- оставляет замечания в одном цикле приемки;
- явно пишет OK;
- может остановить работу или изменить ее границы.

### Improver

- собирает замечания цикла;
- ищет системную причину;
- предлагает изменения инструкций, руководств и процессов в собственных Issue и PR;
- возвращает обратный вызов с готовым к проверке результатом, который ещё не разблокирует зависимую реализацию;
- не меняет продуктовое решение без отдельной приемки.

## Версионирование приемки

Приемка связана с версией результата, хешем, коммитом или SHA PR. Существенное изменение после OK отменяет приемку. Рецензент фиксирует итоговые доказательства и точную версию перед обратным вызовом менеджеру.

Любой новый коммит после `APPROVE` требует нового полного прохода. Рецензент явно пишет, что проверил всю ветку относительно базовой ветки, перечисляет проверенный SHA и не переносит вывод с предыдущей версии автоматически.

## Таблица решений владельца

Существенные развилки ведутся в одной таблице со столбцами: решение, статус, активный вариант, источник и дата, альтернативы, затронутые PR, риски, миграция и откат.

Допустимые статусы:

- `open` — владелец ещё не выбрал вариант; рекомендация не является активным выбором;
- `selected` — на промежуточном ручном шлюзе выбран ровно один активный вариант, но полный повторный проход и финальный OK результата ещё не завершены;
- `final` — выбор входит в результат, принятый владельцем для точной версии или SHA.

В статусах `selected` и `final` активен ровно один вариант. Отклонённые и аварийные альтернативы не удаляются: они остаются историей с последствиями. После выбора исполнитель распространяет его по краткому выводу, составу и порядку PR, критериям, рискам, зависимостям, миграции и откату. Несогласованное место блокирует следующий шлюз.

## Проверка GitHub и CI

- Проверка обсуждений выполняется с учетом тредов `reviewThreads`; число плоских комментариев не заменяет число разрешённых и неразрешённых тредов.
- `APPROVE` относится к точному SHA. После нового коммита, содержательного комментария или нового `CHANGES_REQUESTED` готовность проверяется заново.
- Отсутствие проверок, пустой `statusCheckRollup` и отсутствие статусов коммита фиксируются как «GitHub `check runs` отсутствуют», а не как успешный CI.
- Локальные команды и проверки GitHub перечисляются раздельно. Если проверки отсутствуют, ручной шлюз показывает ограничение и требует осознанного решения владельца для точного SHA.
- Документированные будущие проверки считаются планируемыми шлюзами приёмки, пока не выполнены фактически.

## Обратный вызов рецензента после финального OK

После финального OK владельца рецензент выполняет отдельную неизменяющую проверку и возвращает менеджеру:

- точный SHA ветки, принятый владельцем, и подтверждение, что он не изменился;
- базовую ветку PR и фактический `main`;
- состояние проверок GitHub и статусов коммита без подмены отсутствия успехом;
- число разрешённых и неразрешённых тредов;
- новые коммиты, рецензии и комментарии после финального OK;
- защиту ветки, очередь слияния, возможность слияния и иные блокеры;
- явный вывод, требуется ли повторная приемка.

Рецензент не снимает draft и не выполняет слияние.

## Слияние менеджером

Менеджер сливает только после финального OK и обратного вызова рецензента по проверке после OK. Перед слиянием он повторно читает SHA ветки и использует `--match-head-commit` или эквивалентную защиту от подмены принятого SHA.

После слияния обычного принятого результата менеджер:

1. выполняет свежий `git fetch` и подтверждает новый `main` и коммит слияния;
2. подтверждает, что в слияние вошёл принятый SHA ветки;
3. проверяет состояние PR и закрытие связанной Issue;
4. фиксирует фактическое состояние проверок GitHub и ограничения;
5. проверяет отсутствие неожиданных новых коммитов, рецензий и комментариев, меняющих результат;
6. запускает `improver` через MCP и передаёт весь цикл обратной связи;
7. после обратного вызова `improver` проводит отдельные Issue и PR улучшения процесса через независимое полное рецензирование, ручные шлюзы владельца и проверку после финального OK;
8. сам сливает принятый результат `improver` с защитой точного SHA;
9. только после этого запускает массовую следующую зависимую реализацию.

После слияния PR улучшения процесса менеджер подтверждает SHA и состояние PR по тем же правилам, завершает исходный цикл `improver` и не выполняет пункт 6 рекурсивно. Отдельный новый запуск допустим только по новому материальному замечанию с явным обоснованием, а не из-за самого факта слияния.

Если Issue не должна закрываться этим PR, это явно указано в жизненном цикле; ложная формальная зависимость или автоматическое закрытие не добавляются.

## Параллельность

После слияния обычного общего зависимого результата менеджер сначала принимает и сливает отдельный результат `improver`. Затем он может запускать несколько независимых волн: например, после принятия шаблона сервиса и правил контрактов разные доменные сервисы разрабатываются параллельно в отдельных обсуждениях.

Нельзя параллельно реализовывать несколько потребителей нестабильного контракта до его приемки, если это приведет к массовой переделке.

## Жизненный цикл GitHub для кодового результата

1. Issue фиксирует цель, результат, критерии и зависимости текстом; формальная dependency/sub-issue связь добавляется только при точном соответствии семантике.
2. Исполнитель открывает черновик PR.
3. Циклы рецензирования выполняются в inline-замечаниях и итоговых комментариях.
4. Менеджер публикует готовое для владельца резюме со ссылками и доказательствами.
5. Замечания владельца отрабатываются в том же PR, если границы работы не изменились принципиально.
6. Рецензент полным проходом подтверждает закрытие тредов `reviewThreads`, проверки и точный SHA.
7. Владелец дает финальный OK.
8. Рецензент выполняет проверку после финального OK и возвращает менеджеру обратный вызов с итоговыми доказательствами и блокерами слияния.
9. Менеджер выполняет слияние с защитой `--match-head-commit` и подтверждает новый `main` и закрытие Issue.
10. Менеджер через MCP запускает `improver` со ссылками на Issue, PR, треды рецензирования, рецензии, решения владельца и периодом.
11. После обратного вызова `improver` менеджер проводит отдельный результат улучшения процесса через жизненный цикл ниже.

## Жизненный цикл GitHub для результата improver

1. `improver` создаёт или обновляет отдельные Issue и PR с категориями исходной обратной связи и точными границами изменения процесса.
2. Независимый рецензент полным проходом проверяет весь head относительно base; исправления проходят повторный полный проход.
3. Владелец проходит ручные шлюзы и даёт финальный OK для точного SHA.
4. Рецензент выполняет проверку после финального OK и возвращает менеджеру итоговые доказательства и блокеры слияния.
5. Только менеджер сливает результат `improver` с защитой принятого SHA и подтверждает состояние после слияния.
6. Слияние разблокирует зависимую реализацию и завершает исходный цикл `improver`; новый `improver` из-за этого слияния не запускается.
7. Новый цикл возможен как отдельная явно обоснованная работа только при новом материальном замечании.

## Дочерние треды и обратные вызовы

1. Перед межкомнатным запуском менеджер проверяет каталог через `mattermost_list_chats(target_agent)`, затем полную карточку выбранного чата через `mattermost_get_chat(chat)` и передаёт параметр `owner_mention` и контракт возврата `post_id` прямо в `message` вызова `mattermost_start_agent_thread`. Текущее значение проекта MatterCodex — `@lepehovsv`; переиспользуемый шаблон не зашивает его как универсальное.
2. Успешный `mattermost_start_agent_thread` сначала создаёт дочерний тред, ставит запуск целевого агента в долговечную очередь и создаёт предусмотренные платформой событие аудита и служебное сообщение с признаком `notrigger`.
3. Только запущенная после этого дочерняя сессия вызывает в собственном текущем треде `mattermost_post_thread_update`, публикует отдельное короткое сообщение с точным `@username` владельца и сохраняет возвращённый ей `post_id`.
4. Дочерний агент включает собственный `post_id` в `mattermost_return_to_requester`.
5. Менеджер проверяет наличие и соответствие `post_id` в обратном вызове. Доступный `mattermost_post_thread_update` не позволяет менеджеру выбрать уже созданный дочерний тред, и процесс не предполагает отсутствующий MCP с выбором целевого треда. Само упоминание не запускает агента.
