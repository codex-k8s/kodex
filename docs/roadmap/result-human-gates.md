# Шлюзы качества и ручной приемки по типам результата

## Принцип

Проект выбирает версионируемый режим поставки. Режим определяет число проверок и
ручных шлюзов, но не отменяет защиту секретов, данных, trust boundary,
миграционной совместимости и обязательного тестового контура.

Поддерживаются два режима:

- `release` — полный цикл приемки для промышленного выпуска и рискованных
  изменений;
- `prototype-accelerated` — ограниченный по сроку режим быстрой разработки,
  явно разрешенный владельцем для заданного набора результатов.

Активный форсированный план MatterCodex описан в
[ROAD-MC-007](accelerated-mvp-prototype.md). Имена ролей не определяют
полномочия: исполнителя, независимую и security-проверку выбирает policy
revision проекта.

## Ускоренный цикл

```text
Менеджер фиксирует один проверяемый результат и границы
  -> Исполнитель открывает отдельные ветку и PR
  -> Один независимый review pass и один security pass запускаются параллельно
  -> Исполнитель одним циклом исправляет Merge blocker
  -> Авторы проверок подтверждают только свои исправленные blocker или создают follow-up Issues
  -> Менеджер проверяет точный SHA, тесты и ноль unresolved reviewThreads
  -> Менеджер сливает с защитой от смены SHA
  -> Отдельные post-merge reviewer и security проверяют merge commit
  -> Новые неблокирующие находки попадают в backlog
```

Повторный полный проход до слияния не является обязательным. Он нужен только
автору конкретного `Merge blocker`, чтобы подтвердить его устранение, либо если
границы PR materially изменились. Владелец не принимает каждый PR отдельно,
если заранее одобрил границы ускоренной волны. Ручное внимание требуется для
нового продуктового решения, необратимой миграции, опасного deploy или
неустранимого blocker.

## Режим release

В режиме `release` менеджер назначает дополнительные проходы, ручную приемку
точного SHA и проверку после OK сообразно риску. Этот режим обязателен для
публичного или коммерческого выпуска, восстановления из backup, изменения
trust boundary, destructive migration и rollout без доказанного отката.

## Триаж замечаний

Каждое замечание независимой или security-проверки получает ровно один исход:

1. `Merge blocker` — активная утечка секрета, потеря или повреждение данных,
   нарушение принятой trust boundary, необратимый миграционный тупик, ложный
   обязательный контракт либо неработающий обязательный тестовый контур.
   Замечание исправляется в текущем PR.
2. `MVP follow-up` — изолированный риск, который безопасно устранить отдельным
   изменением. Автор создаёт Issue с labels `mvp-follow-up` и предметным label,
   отвечает в исходном thread URL Issue и причиной безопасной отсрочки, затем
   разрешает thread.
3. `Informational` — изменение не требуется. Автор оставляет проверяемое
   объяснение и разрешает thread без Issue.

Молча опускать находки запрещено. Плоский список комментариев не заменяет
GitHub GraphQL `reviewThreads` и `resolved`. Отсутствие `check runs` не является
успешным CI; менеджер фиксирует ограничение и принимает его только в границах
действующей policy revision.

## Ответственность до слияния

### Менеджер

- не смешивает независимые результаты в одном PR;
- передаёт reviewer и security одинаковую классификацию замечаний;
- запускает один независимый и один security pass параллельно;
- не требует исправлять `MVP follow-up` в текущем PR;
- после исправлений проверяет точный head SHA, фактические проверки и ноль
  unresolved threads;
- сливает только разрешённый policy revision результат с
  `--match-head-commit` или эквивалентной защитой;
- не запускает `improver` после каждого слияния.

### Исполнитель

- создаёт результат и проверяемые доказательства;
- исправляет все `Merge blocker` одним сфокусированным циклом;
- отвечает на каждое замечание и не разрешает чужой thread;
- не расширяет границы PR ради follow-up долга.

### Reviewer и security

- выполняют один полный проход исходного head в своей области ответственности;
- публикуют прикладные inline findings и итог, привязанные к SHA;
- после исправлений проверяют только собственные blocker и затронутый ими
  контракт, если границы PR не изменились;
- создают follow-up Issue до разрешения отложенного thread;
- не сливают PR и не выбирают следующий этап.

## Post-merge аудит

После слияния менеджер или директор запускает отдельными дочерними работами
reviewer и security на точный merge commit. Эта проверка не переписывает
историю принятого PR и по умолчанию не блокирует независимые волны.

- срочный дефект с риском утечки, потери данных или эксплуатации получает
  `mvp-blocker` и отдельный hotfix-поток;
- прочие находки получают `mvp-follow-up` и предметный label;
- в слитом PR публикуются ссылки на созданные Issues;
- исправления выполняются отдельными ветками и PR.

## Ежедневный improver

`improver` запускается один раз в сутки вечером по локальному времени проекта,
а не после каждого merge. До реализации `AutomationSchedule` запуск выполняет
директор по явному ежедневному заданию.

Improver выбирает merged PR без label `improved` за обрабатываемый период,
анализирует review threads, post-merge Issues и замечания владельца и создаёт
один сфокусированный PR инструкций либо фиксирует, что изменений не требуется.
После успешной обработки он добавляет каждому просмотренному PR label
`improved`. Слияние собственного PR не запускает improver рекурсивно.

Исторические merged PR до включения режима получают `improved` как базовая
отметка: это означает, что они не входят в первый ежедневный batch, а не
доказывает отсутствие технического долга.

## Параллельность

В `prototype-accelerated` одновременно допускается до шести независимых волн.
Директор ведёт реестр активных работ, не запускает два PR на одну мутацию и не
обходит явную dependency. Подготовка зависимого контракта может идти
параллельно, но поведенческое переключение ждёт принятого prerequisite.

`MVP follow-up`, post-merge аудит и ежедневный improver не занимают критический
путь, если не создали Issue с label `mvp-blocker`.

## Жизненный цикл GitHub

1. Issue фиксирует цель, границы, критерии, dependency и delivery mode.
2. Исполнитель открывает отдельный PR с ручным сценарием проверки.
3. Reviewer и security выполняют по одному параллельному проходу.
4. Исполнитель исправляет `Merge blocker`; отложенные находки оформляются
   Issues и связываются с threads.
5. Менеджер проверяет head/base SHA, тесты, mergeability и `reviewThreads`.
6. Менеджер сливает с защитой точного SHA и подтверждает новый `main`.
7. Post-merge reviewer и security проверяют merge commit и пополняют backlog.
8. Вечерний improver обрабатывает merged PR без `improved` единым batch.

Если владелец оставляет замечания уже после merge ускоренного PR, они становятся
отдельной Issue/hotfix, а не поводом возвращать слитую ветку.

## Волны и обратные вызовы

1. Координатор проверяет каталог через `mattermost_list_chats(target_agent)` и
   карточку выбранного чата через `mattermost_get_chat(chat)`.
2. Верхнеуровневый координатор через `mattermost_start_agent_thread` создаёт в
   рабочем чате отдельный тред координатора волны, наследует root initiator и
   ставит запуск в долговечную очередь.
3. Координатор волны через `mattermost_request_agent` запускает рабочих и
   проверяющих участников в том же треде. Каждый такой запуск хранит точный
   долговечный маршрут возврата.
4. Дочерняя сессия возвращает результат через
   `mattermost_return_to_requester`; callback получает только разрешённая роль.
   Если явный вызов пропущен, платформа один раз использует финальный ответ как
   аварийный callback.
5. Обычные статусы и callbacks не упоминают инициатора. Для решения или
   критического blocker используется `mattermost_request_owner_attention`.
6. Окончательная runtime-ошибка после retry policy уведомляет root initiator
   один раз и содержит безопасную цепочку запусков.
