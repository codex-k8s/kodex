# Подготовка рабочей области MatterCodex

Подготовка выполняется после слияния базовой документации. Операция сначала читает действующее состояние и переиспользует существующие учетные записи и интеграции без создания дублей.

## Рабочая область

- Имя: `MatterCodex`.
- Slug команды: `matter-codex` либо свободный согласованный вариант.
- Mattermost: отдельная команда.
- Владелец GitHub: `codex-k8s`.
- Репозиторий: `codex-k8s/matter-codex` как необязательный контекст интеграции для разработки.
- Локаль: русский язык.
- Владелец конфигурации: интерфейс на первом этапе; переход к Git после волны GitOps.
- Project advanced settings содержат
  `{"coordination_mode":"manager-only"}`. Bootstrap создает новую immutable
  policy revision `manager-unit-v1`, оставляет в `coordination` только manager
  и не восстанавливает необязательную роль director.

## Агенты

- `manager` — корневая координация максимум двух unit и дочерняя координация
  одного unit; PR не сливает.
- `product-manager` — продуктовые требования, бэклог и отчеты.
- `architect` — домены, контракты, границы сервисов и ADR.
- `developer` — реализация серверных компонентов Go и среды выполнения.
- `frontend` — центр управления на Vue.
- `reviewer` — архитектурное рецензирование с обратным вызовом менеджеру.
- `docs` — согласованность документации.
- `qa-bot` — сквозные и регрессионные проверки с доказательствами.
- `sre` — развертывание, эксплуатация, резервное копирование и наблюдаемость.
- `security` — модель угроз, интеграции, секреты и цепочка поставки.
- `ui-designer` — пользовательские сценарии, варианты и визуальные макеты.
- `improver` — перенос замечаний в инструкции и руководства.
- `mattercodex-admin` — аварийная диагностика и настройка платформы с отдельной политикой риска.

Каждый агент получает отдельную учетную запись бота Mattermost. Существующие учетные записи OpenAI и GitHub выбираются по назначению и полномочиям; секретные значения не копируются в промпты или документы.

В текущем dogfooding-инстансе manager и developer намеренно используют один
второй OpenAI account binding. Это операционная настройка инстанса, а не
зашитое имя учетной записи; prompt и seed не должны зависеть от account alias.

Роль `security` создается при подготовке области и работает параллельно с догфудингом. Она ведет реестр известных рисков текущей платформы и проверяет новые решения, затрагивающие авторизацию, секреты, права интеграций, опасные MCP-вызовы, файлы, кластерный доступ и цепочку поставки. Полный аудит и устранение известных некритических рисков текущего развертывания не блокируют начало догфудинга или первую архитектурную волну. Менеджер подключает `security` до реализации рискованного решения и перед слиянием его реализации. Остановить соответствующую реализацию или развертывание может только подтвержденный критический риск, например утечка секрета, публичный административный доступ или удаленное выполнение команд без авторизации.

## Комнаты

- `coordination` — владелец и корневой manager, эпики и human gates;
- `development` — отдельный тред дочернего manager на каждый unit.

Старые тематические комнаты архивированы, а их треды закрыты для новых
запусков. История сохраняется для аудита. Новые системные комнаты `runs` и
`incidents` создаются соответствующими unit после реализации их контрактов.

## Начальные эпики GitHub

Источник правды: umbrella #179, эпики #180-#185 и sub-issues #186-#197.

## Начальные расписания

После реализации расписаний:

- ежедневный `improver` по merged PR без label `improved`; после обработки он добавляет label, а слияние собственного результата не создаёт рекурсивный запуск;
- проверка работоспособности платформы от `mattercodex-admin`;
- проверка возраста резервных копий и доказательств восстановления от `sre`;
- еженедельное резюме менеджера по активным эпикам.

## Приемка подготовки

- Владелец состоит в команде и комнатах.
- Все боты ролей видимы и имеют корректные имена.
- Учетные записи и интеграции показывают фактические права без секретов.
- Репозиторий доступен через выбранную интеграцию GitHub.
- Manager отвечает в комнате `coordination`, а unit создаётся новым
  manager-тредом в `development`.
- Необязательная роль director выключена и не состоит в активных комнатах.
- Проверка делегирования не использует упоминание как триггер.
- Ничего не запускается автоматически до стартовой команды владельца.
