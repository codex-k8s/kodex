# Инструкции проекта matter-codex

## Общие правила

- Ответы пользователю, статусы, PR-описания и документацию писать по-русски.
- Сообщения коммитов писать на английском языке.
- Перед началом работы читать этот файл и проверять текущую ветку.
- Секреты из `.env`, kubeconfig, GitHub, OpenAI и Mattermost не выводить в сообщения, логи, PR и промпт.
- Значения переменных окружения не документировать. Допустимо документировать только имена ключей и факт, что значение задано.
- Для актуальной информации по библиотекам использовать Context7 MCP.
- Перед изменением архитектуры читать `docs/architecture/**`, `docs/domains/**` и релевантные ADR из `docs/decisions/**`.
- Для реализации использовать `docs/guides/**`, `docs/design-guidelines/AGENTS.md`, `docs/design-guidelines/common/check_list.md` и профильный список проверок.
- Для OpenAI и Codex использовать официальную документацию OpenAI или руководство Codex.
- Для GitHub-операций использовать соответствующие навыки GitHub.

## Язык

- Ответы агентов, документацию, GitHub Issues, заголовки и описания PR, комментарии рецензирования и комментарии в коде писать по-русски.
- Сообщения коммитов писать на английском языке согласно правилам раздела выше.
- Английский сохранять для идентификаторов кода, имен файлов, API и протоколов, имен переменных окружения и секретов, команд, внешних канонических статусов и сообщений технических логов.
- Не смешивать русский и английский в обычной проектной прозе, если существует точный и понятный русский термин.

## Git и PR

- Работу вести в отдельных ветках.
- `main` использовать только как базовую ветку.
- Каждый PR должен быть вручную тестируемым владельцем.
- В PR явно писать, что можно проверить вручную и какие автоматические проверки запускались.
- Если в процессе найдено противоречие между документацией, окружением или запросом владельца, остановиться и предложить варианты.

## Kubernetes и окружение

- Целевая среда выполнения MVP работает в Kubernetes.
- Сценарии первоначальной настройки и развертывания читают `.env`, но печатают только безопасные состояния проверок.
- Pod агента получает только необходимые секреты и только через Kubernetes Secret, переменные окружения или подключенный файл.
- У каждого запуска агента должен быть собственный рабочий каталог и PVC.
- Для MVP выбран один namespace среды выполнения Mattermost: Mattermost, bot-service, pod агента и PVC живут в нем. Имя берется из `MATTERCODEX_NAMESPACE` или `PRODUCTION_NAMESPACE`, если владелец не попросит пересмотреть решение.

## Документация

- Активные продуктовые решения хранить в `docs/product/**`.
- Активную системную архитектуру и границы данных хранить в `docs/architecture/**` и `docs/domains/**`.
- Существенные решения оформлять ADR в `docs/decisions/**`.
- Правила реализации хранить в `docs/guides/**` и детальных `docs/design-guidelines/**`.
- Промышленный эксплуатационный контракт хранить в `docs/operations/**`, а пошаговые действия — в `docs/runbooks/**`.
- Волны, условия приемки результатов и процесс внутреннего использования хранить в `docs/roadmap/**`.
- `docs/strategy/**` является замененной основой MVP и не используется как источник новых решений.
- Исходные документы идеи находятся в `docs/idea/**`.
- Документы должны описывать целевое состояние и явно помечать принятые и открытые решения.

## Ручная приемка и агентная работа

- Ручная приемка относится к законченному типу результата, а не к каждому внутреннему шагу.
- Перед межкомнатным запуском координатор проверяет каталог и карточку целевого чата. Запуск, callback, синхронизация и обращение к инициатору разрешаются только версионируемой политикой проекта; имя и `role_type` роли не являются источником полномочий. Дочерняя роль возвращает результат разрешенному координатору через MatterCodex MCP без обязательного упоминания владельца. Ручной шлюз создается отдельным MCP-инструментом внимания инициатора.
- По умолчанию результат проходит 2-3 цикла рецензирования и исправления до первой приемки владельцем.
- После замечаний владельца исполнитель исправляет результат, рецензент выполняет полный повторный проход, владелец дает финальный OK.
- После любого изменения SHA ветки прежнее одобрение не переносится автоматически: рецензент проверяет весь результат, а не только последнюю разницу, и привязывает вывод к точному SHA.
- Состояние рецензирования проверяется по тредам GitHub `reviewThreads` и их `resolved`-статусу; плоский список комментариев не доказывает отсутствие открытых замечаний.
- Отсутствие GitHub `check runs` не является успешным CI. Такое ограничение явно указывается на ручном шлюзе и может быть принято владельцем только осознанно для точного SHA.
- Все рабочие агенты и рецензент после завершения своей части отправляют долговечный обратный вызов разрешенному координатору через MatterCodex MCP.
- Координатор отслеживает параллельные работы и после каждого обратного вызова решает: запустить следующего агента, дождаться других результатов, вернуть работу на исправление или открыть ручной шлюз.
- После финального OK рецензент отдельно проверяет точный SHA, базовую и основную ветки, фактическое состояние CI и проверок GitHub, открытые треды, новые коммиты и комментарии, защиту ветки и иные блокеры слияния.
- Слияние выполняет только менеджер после финального OK владельца и отдельного обратного вызова рецензента по проверке после OK, с защитой от смены SHA ветки; затем менеджер подтверждает новый `main`, состояние PR и закрытие связанной Issue.
- После слияния обычного принятого результата менеджер запускает `improver` через MCP для обновления инструкций, руководств и управляемых процессов по замечаниям цикла.
- Отдельный результат `improver` оформляется в собственных Issue и PR, проходит независимый полный проход рецензента, ручные шлюзы владельца и сливается только менеджером.
- Обратный вызов `improver` не разблокирует зависимую реализацию: она разрешена только после принятия и слияния отдельного результата улучшения процесса.
- Слияние PR улучшения процесса завершает исходный цикл `improver` и само по себе не запускает `improver` рекурсивно. Новый цикл возможен только как отдельная явно обоснованная работа по новому материальному замечанию, а не автоматически из-за самого слияния.
- Агенты запускают других агентов только через инструменты MatterCodex MCP; текстовые упоминания от учетных записей ботов не являются сигналом запуска.
- Обычное завершение роли не тегает инициатора. Верхнеуровневый координатор открывает плановые ручные шлюзы; координатор волны обращается к инициатору только при разрешенном срочном блокере или прямом человеческом запуске; платформа уведомляет корневого инициатора после окончательной ошибки.
- Названия стандартных ролей являются пресетами, а не зашитыми системными типами. Любой проект может переименовать роли и настроить разрешенные связи без изменения кода.

Детальный контракт шлюзов, таблиц решений, доказательств и слияния определен в `docs/roadmap/result-human-gates.md`.

## Стандартные роли

- `manager` — владеет планом, очередностью работ, обратными вызовами, ручной приемкой, слиянием и запуском `improver`; остальные роли не обходят его при координации процесса.
- `product-manager` — ведет продуктовые требования, сценарии, бэклог и отчеты, не подменяя решения владельца.
- `architect` — проектирует домены, контракты, границы сервисов, данные и ADR; существенные развилки выносит владельцу.
- `developer` — реализует согласованный результат в отдельной ветке и PR, добавляет проверки и устраняет замечания.
- `frontend` — отвечает за интерфейс Vue и TypeScript, доступность, адаптивность и соответствие утвержденным макетам и контрактам.
- `reviewer` — независимо проверяет результат, оставляет замечания и возвращает вывод менеджеру; не сливает PR и не координирует следующий этап.
- `docs` — поддерживает согласованность документации, терминов, ссылок и требований.
- `qa-bot` — составляет и выполняет сквозные и регрессионные сценарии, прикладывает проверяемые свидетельства и заводит дефекты.
- `sre` — отвечает за инфраструктурный код, развертывание, наблюдаемость, резервное копирование и восстановление; опасные действия выполняет только после отдельного разрешения.
- `security` — независимо проверяет модель угроз, секреты, права интеграций, цепочку поставки и риски внешних действий; возвращает замечания менеджеру.
- `ui-designer` — готовит варианты пользовательских сценариев и макетов, затем оформляет выбранный вариант изображениями и Markdown-описанием.
- `improver` — после слияния обычного принятого результата либо как отдельная работа по новому материальному замечанию обобщает обратную связь и улучшает инструкции, руководства, шаблоны ролей и управляемые процессы отдельным проверяемым изменением.
- `mattercodex-admin` — диагностирует и настраивает MatterCodex и его кластер в рамках отдельного административного профиля и политики риска.
